1 基础概念与数据结构

1.1 Redis中常见的数据类型有哪些?

Redis 的数据结构包含：

  1. 基础类型：String、List、Set、Hash 以及 Zset
  2. 进阶类型（Redis 6.0 后引入或强调）：HyperLogLog、Stream、Bitmap 等

1.2 String 的底层实现是什么？什么是 SDS？

Redis 中的 String 主要有三种编码方式：

  1. int
    存储数字类型，即用 long 表示的整数。

  2. embstr
    当字符串长度较小时使用。它分配的是一次性连续内存，因此对缓存非常友好。

  3. raw
    当字符串长度较大时使用。它支持二次内存分配。

1.2.1 什么是 SDS？

SDS（Simple Dynamic String）是 Redis 自己构建的一种字符串结构。Redis 根据字符串长度的不同，定义了不同的 SDS 结构，例如 SDS_SDR5、SDS_SDR8 等。

SDS 的主要结构不仅存储了数据，还包含了：

  • len：数据的长度
  • alloc：分配的空间大小
  • flags：标志位，用于标识所属的类型

1.2.2 SDS 的优势

  1. 获取长度的复杂度为 O(1)
    由于结构中存储了 len 属性，不需要每次通过遍历来获得长度，直接在数据结构中即可获取。

  2. 防止缓冲区溢出
    在进行字符串拼接之前，SDS 会先检查空间大小。如果空间不够，它会自动进行扩容。

  3. 空间预分配
    在扩容时，如果修改后的字符串大小小于 1 MB，SDS 会额外分配与 len 同样大小的未使用空间；如果大于 1 MB，则会多分配 1 MB 的未使用空间。这为后续的追加操作提供了更多冗余空间，减少了内存重分配次数。

  4. 惰性空间释放
    当字符串缩短时，Redis 不会立即回收内存，而是只更新长度，将多余的空间保留在总分配空间中，等待将来使用。

  5. 二进制安全
    SDS 不是以 “\0”（空字符）来标识结尾，而是通过 len 来判断是否结束，因此它可以存储任意的二进制数据。

  6. 兼容 C 语言函数
    SDS 在末尾依然增加了 “\0”，以便兼容部分 C 语言标准的字符串处理函数。

1.3 Zset 的底层实现是什么？

Redis 中 Zset 的底层有两种编码方式：

  1. 紧凑列表（ziplist）
    当数据量比较少时，它采用紧凑列表。其特点是将所有数据紧挨着存放在一块连续的内存中，非常节省空间。但在进行插入或修改操作时，需要重新分配和移动内存。

  2. 跳表（skiplist）加字典（dict）
    当元素较多或内存占用较大时，会采用跳表加字典的方式。这二者是相互配合的关系：
    (a) 哈希表更擅长单点查询，效率非常快。
    (b) 跳表则更加擅长范围查找和排名。

关于跳表的具体结构与实现：

  1. 本质与结构
    跳表本质上是一个增加了多级索引的链表。在最底层包含所有节点的完整有序列表；在上层则建立索引层，从底层列表每隔几个节点抽出一个节点，形成更加稀疏的列表。层级越高，节点越少，跨度越大。

  2. 查找过程
    利用二分查找的思想，从最高层开始查找。如果当前节点的下一个节点值小于目标值，就向右走；如果大于等于目标值，则往下一层走。重复此过程，直到找到目标节点。

  3. 内部组成
    跳表的节点结构包含成员对象、分数（score）、后退指针以及层级列表：
    (a) 成员对象与分数：用于存储数据及计算排名。
    (b) 后退指针：使得跳表能像双向链表一样从后往前遍历，方便排序和处理。
    (c) 层级列表：包含指向下一层的指针以及跨度（span）。跨度记录了当前节点到下一个节点之间跨越了多少个节点，其主要作用是计算排名和辅助范围查找。

Redis 中每个跳表节点大致包含：

  • score：分数
  • ele：成员对象
  • 多层 forward 指针：指向每一层的下一个节点
  • backward 指针：底层的前驱节点，方便反向遍历

跳表的插入过程如下：

  1. 定位插入位置
    首先从高层往下找，记录每一层中最后一个小于当前要插入节点数值的点。例如，要插入一个 score 等于 6 的节点，系统会从高层开始往下寻找小于 6 的节点。

  2. 记录路径
    将每一层找到的这些小于 6 的节点存储在 update 数组里，作为后续插入位置的前驱节点。

  3. 确定节点层数
    节点的层数不是固定的，而是通过“抛硬币”的方式随机生成的。根据概率决定层高，层级越高，节点数越少，从而形成类似索引的结构。

  4. 插入新节点
    (a) 确定好层级后，将新指针插入到每一层对应的位置。
    (b) 如果新节点的层数比当前跳表的最大层数还要高，则需要更新跳表的最大层数。

删除操作与插入类似：

  1. 先找到目标节点。
  2. 记录每一层的前驱节点。
  3. 让前驱节点直接跳过目标节点，并调整相关指针。

为什么插入时要选择随机决定层数？
这样可以从概率上保证平衡。例如，1/4 的节点能够到达第二层，1/16 的节点到达第三层，1/64 的节点到达第四层。通过这种方式，可以保证层级越高，节点数越少，使跳表的整体效率在概率上趋于平衡。

1.4 Hash 的底层实现是什么？

1.4.1 rehash

  1. 分配空间：触发 Rehash 时，Redis 为 dict 的 ht[1] 分配空间（扩容时大小为第一个大于等于 ht[0].used * 2 的 2n；缩容时为第一个大于等于 ht[0].used 的 2n）。
  2. 设置标志：将 rehashidx 设为 0，表示 Rehash 工作正式开始（-1 表示未进行）。
  3. 分批迁移：在此期间，每次对字典执行增删改查（如 HSET, HGET）操作时，程序除了执行指定操作，还会顺带将 ht[0] 在 rehashidx 索引位置上的所有键值对迁移到 ht[1]，然后将 rehashidx++。 (另外，Redis 还会在定时任务中顺带搬运一些 bucket，防止长期没有请求时 Rehash 迟迟无法完成)
  4. 访问规则：在 Rehash 进行期间，查找操作会先查 ht[0]，找不到再去 ht[1]；新增操作则一律只加到 ht[1]，保证 ht[0] 的数据只减不增。
  5. 收尾交接：随着操作不断进行，最终 ht[0] 的所有节点都会迁移到 ht[1]。此时，将 ht[1] 设为 ht[0]，释放旧的 ht[0]，创建一个新的空 ht[1]，并将 rehashidx 重置为 -1，Rehash 结束。

1.5 Redis 为什么这么快?

Redis 运行快的原因主要包括：

  1. 绝大部分请求是在内存中完成的。
  2. 采用单线程模型，避免了频繁的上下文切换和锁竞争。 主要指网络 IO 和键值对读写，避免上下文切换和竞争条件
  3. 使用了 I/O 多路复用机制。
  4. 拥有非常高效的数据结构设计。

1.6 为什么Redis设计为单线程？6.0版本为何引入多线程？

1.6.1 Redis 最初设计为单线程的原因

  1. 内存操作性能极高
    Redis 是在内存中进行操作的，执行速度非常快。其主要的性能瓶颈通常不在 CPU，而是在网络 I/O 上。

  2. 早期网络 I/O 需求较低
    在早期阶段，网络 I/O 并不频繁，单线程的处理能力足以支撑当时的业务需求。

  3. 避免上下文切换
    使用单线程可以避免频繁的 CPU 上下文切换，从而减少了额外的性能开销。

  4. 简化设计与无锁机制
    单线程模式下不需要设计一套复杂的防止并发的机制（如锁机制），直接执行命令即可，这大大降低了系统的复杂度。

1.6.2 版本引入多线程的原因

随着业务发展，网络 I/O 确实成为了 Redis 的性能瓶颈。为了进一步提升性能，6.0 版本引入了多线程来专门处理网络 I/O 的读写。

但需要注意的是，Redis 的命令执行依然是由单线程操作的，这确保了其依然能够保持原子性。

2 持久化机制

2.1 RDB 和 AOF 的区别是什么？

首先，Redis 为什么需要持久化呢？

因为在 Redis 重启之后，如果不做持久化，其内存中的数据就会全部丢失。如果机器宕机，数据也会丢失。因此，我们需要将数据以某种方式保存到磁盘里，以便在重启后重新加载。

Redis 一共有两个非常经典的持久化机制：AOF 和 RDB。此外，Redis 4.0 又引入了混合持久化。

关于 RDB（Redis DataBase）：

  1. 基本概念
    RDB 本质上是一个数据快照。它是在某一时刻对 Redis 中所有数据进行快照处理，并保存到磁盘的二进制文件中。通过加载这个二进制文件，就可以在 Redis 启动时将数据恢复。

  2. 主要特点
    (a) 恢复速度快：因为它直接加载二进制文件，所以效率非常高。
    (b) 文件体积小：适合做数据备份。

  3. 缺点
    (a) 数据丢失风险：RDB 属于定期快照。例如每 5 分钟做一次快照，如果在第 4 分钟时 Redis 宕机，那么前 4 分钟的数据就会丢失。
    (b) 性能开销：生成快照时会 fork 子进程，这会带来一定的耗时和页面复制成本。

  4. 触发方式
    (a) 自动触发：可以设定多长时间触发一次，或者在多长时间内有多少个 key 发生变化就触发一次。
    (b) 手动触发：
    - 前台执行：同步执行会导致主线程阻塞，不推荐使用。
    - 后台执行：通过 fork 子进程来进行快照处理，主进程可以继续处理其他请求。

AOF 持久化机制
AOF（Append Only File）会将你执行的每一条写操作命令都记录到文件中。在 Redis 重启时，通过重新执行这些命令文件，就可以实现数据恢复。

  1. AOF 的写入流程：
    在写入 AOF 文件时，系统会先将命令写入到 AOF 缓冲区，再根据指定的策略决定何时将其真正刷新到磁盘中。

  2. AOF 的三种刷盘策略：
    (a) Always：每条写命令都立即进行刷盘。
    (b) Everysec：每秒刷盘一次。
    (c) No：由操作系统决定何时进行刷盘。

  3. AOF 的优缺点：
    (a) 优点：
    - 数据更安全：因为它记录的是写操作。在每秒刷盘（Everysec）模式下，即使发生宕机，最多也只会丢失一秒钟的数据。
    - 可读性强：由于记录的是原始命令，而不像 RDB 那样是二进制文件，因此更易于理解和维护。
    - 性能友好：在大多数情况下属于顺序追加写，对磁盘 I/O 比较友好。
    (b) 缺点：
    - 文件体积较大：记录的是每一条命令，文件增长较快。
    - 恢复速度较慢：由于需要逐条执行命令，恢复效率不如 RDB。

如果 AOF 文件长期追加导致体积过大，则需要进行 AOF 重写。

总结一下这两种方式：

  1. RDB
    (a) 记录内容：某一时刻的数据快照
    (b) 恢复逻辑：恢复到某次快照那一时刻的数据
    (c) 文件与性能：文件体积通常更小，恢复速度更快

  2. AOF
    (a) 记录内容：写操作命令
    (b) 恢复逻辑：恢复到最后一次成功写入 AOF 文件时记录的那些操作
    (c) 文件与性能：文件体积通常更大，恢复速度更慢

2.2 Redis 4.0 引入了什么新的持久化方式？

之前提到的 RDB 和 AOF 都有各自的优缺点：

  1. RDB：文件更小，恢复速度更快，但容易丢失数据
  2. AOF：数据安全性更高，不容易丢失数据，但文件体积大，恢复速度慢

为此，Redis 4.0 引入了混合持久化（Mixed Persistence）方式。在 AOF 进行重写时，它会在新的 AOF 文件中进行如下处理：
(a) 前半部分：直接写入当前数据的 RDB 数据快照（二进制格式），确保内容紧凑
(b) 后半部分：追加重写期间产生的增量写命令

这种方式结合了两者的优点：既解决了数据不安全的问题，又保证了较快的恢复速度，同时有效缩小了文件体积。

2.3 AOF 重写机制原理是什么？

AOF 重写机制

  1. 为什么需要 AOF 重写？
    因为 AOF 会记录所有的写命令。如果频繁修改同一个 Key（例如：给 A 加 1，随后又减 1，重复多次），虽然最终 A 的值并没有改变，但 AOF 文件中却记录了多条冗余命令。这会导致 AOF 文件越来越大，且在恢复数据时执行速度非常慢。因此，需要通过 AOF 重写来直接根据当前内存中的数据生成一个新的 AOF 文件。

  2. 触发方式
    (a) 手动触发：通过命令直接触发。
    (b) 自动触发：通过配置达到一定条件后自动触发。例如，当 AOF 文件达到指定大小，或者比上次重写后的体积增长了 100% 时，就会触发重写。

  3. 重写流程
    重写过程采用子进程处理，具体步骤如下：
    (a) fork 子进程：主进程先 fork 出一个子进程。
    (b) 生成新文件：子进程基于当前内存中的数据快照，生成一个新的 AOF 文件。
    (c) 并发处理：在子进程重写期间，主进程继续处理客户端的请求。
    (d) 命令追加：由于主进程仍在处理新的修改命令，这些命令会同时被追加到旧的 AOF 文件中，并写入 AOF 重写缓冲区。
    (e) 合并与替换：当子进程完成重写后，会将重写缓冲区中的增量命令追加到新 AOF 文件的末尾。
    (f) 完成替换：最后，用新的 AOF 文件替换掉旧的 AOF 文件。

通过这种方式，新的 AOF 文件由两部分组成：前半部分是数据快照，后半部分是重写期间的增量命令。这保证了起点处于全量状态，并涵盖了重写期间的所有操作，极大地缩短了重启时的恢复时间。

5 缓存常见问题

5.1 缓存穿透、缓存击穿、缓存雪崩的区别及解决方案？

5.1.1 缓存穿透（Cache Penetration）

定义：
是指用户请求的数据在缓存中没有，在数据库中也没有。由于两端都缺失，每次请求都会直接打到数据库上，缓存起不到保护作用。

解决方案：

  1. 设置缓存空值： 将查询到的空结果也缓存起来，并为其设置一个较短的 TTL（过期时间）。
  2. 布隆过滤器（Bloom Filter）：
    (a) 在业务层之前增加布隆过滤器，将所有可能存在的 Key 都放进去。
    (b) 请求到来时先通过布隆过滤器判断，若判断不存在则直接拦截，不再查询缓存和数据库。
    (c) 优点：非常适合防止恶意攻击。
    (d) 缺点：存在误判的可能性（可能将不存在的数据误判为存在）。
  3. 参数校验： 在业务层增加校验逻辑，拦截非法的请求参数。

5.1.2 缓存击穿（Cache Breakdown）

定义：
指某个热点 Key 在某一时刻突然失效，此时正逢大量并发请求涌入，导致这些请求直接打到数据库，使数据库压力暴增。

解决方案：

  1. 热点数据永不过期： 从热点 Key 入手，不设置物理过期时间，避免其失效。
  2. 使用分布式锁：
    (a) 保证同一时刻只有一个线程可以访问数据库并建立缓存。
    (b) 其他请求必须等待锁释放后，再重新查询缓存。
  3. 设置逻辑过期时间：
    (a) 在 Value 内部设置一个逻辑上的过期时间，而不给 Redis 设置真实的 TTL。
    (b) 读取时若发现逻辑已过期，则先返回旧数据，同时开启后台异步线程去刷新缓存。
    (c) 缺点：在数据更新期间容易出现脏数据。

5.1.3 缓存雪崩（Cache Avalanche）

定义：
指大量的缓存 Key 在同一时间集中过期，或者 Redis 服务整体不可用，导致海量请求瞬间涌向数据库，造成数据库性能下降甚至崩溃。

解决方案：

  1. 随机 TTL： 不让所有的 Key 处于相同的过期时间，采用随机的过期时间来分散压力。
  2. 多级缓存： 增加本地缓存等多级架构，如果 Redis 整体不可用，由其他层级的缓存先挡住流量。
  3. 缓存预热： 在服务器启动初期，先将热点数据手动同步到缓存中，避免启动即高压。
  4. 应用层保护：
    (a) 当缓存失效导致数据库压力过大时，利用限流、熔断和降级等机制进行自我保护。
    (b) 避免数据库直接被打挂，确保核心服务的可用性。

缓存穿透
可以理解为请求去访问一个不存在的 key。 请求一直打到数据库

缓存击穿
指某个热点 key 失效了，导致大量的请求瞬间去访问这个 key。

缓存雪崩
指大面积的 key 同时失效，或者 Redis 宕机，导致请求失去了缓存的保护，从而使数据库的压力暴增。

  • 对不存在的数据：缓存空值 + 布隆过滤器
  • 对热点 key：互斥锁 / 逻辑过期 / 永不过期+异步刷新
  • 对批量 key：TTL 随机化
  • 对整体系统：Redis 高可用 + 限流降级
  • 对极热点：本地缓存 + Redis 多级缓存

5.2 如何保证数据库和缓存的双写一致性？

在数据更新时，数据库和缓存都需要进行更新。为了保证两边的数据一致性，常见的结论是：先更新数据库，再删除缓存。

具体的实现思路和优化方案如下：

  1. 旁路缓存模式（Cache Aside Pattern）
    (a) 读取流程：先读缓存，如果缓存未命中，则查询数据库。查到数据后将其写入缓存，并返回结果。
    (b) 写入流程：先更新数据库，然后再删除缓存。

  2. 潜在的一致性问题
    虽然上述方案是常用做法，但在高并发场景下仍可能导致数据不一致。
    (a) 场景示例：线程 A 查询缓存未命中，随后去数据库查到旧值（如 100）。
    (b) 线程 B 更新数据库为新值（如 200），并删除了缓存。
    (c) 线程 A 将之前查到的旧值（100）回填到缓存中。
    (d) 结果：缓存中是旧值 100，而数据库是新值 200，产生了脏数据。

  3. 双写一致性解决方案

    方案一：延迟双删
    在更新数据库并删除缓存后，先让程序休眠一小段时间，然后再执行一次删除缓存的操作。这主要是为了解决上述“旧值回填”导致的并发问题。

    方案二：消息队列补偿机制
    (a) 先更新数据库，然后将“缓存失效”的消息发送到消息队列（MQ）中。
    (b) 由消费者异步处理删除缓存的操作。
    (c) 如果删除失败，可以通过 MQ 的重试机制进行补偿，直到删除成功。

    方案三：订阅数据库 Binlog
    (a) 业务层只负责更新数据库。
    (b) 使用 Canal 等组件直接订阅数据库的 Binlog。
    (c) 当监听到数据变化后，由 Canal 异步执行删除对应缓存的操作，从而实现最终一致性。

6 分布式锁

6.1 如何使用 Redis 实现分布式锁？

Redis 分布式锁在最开始是基于 SETNX 和过期时间来实现的，但这种方式是非原子性的。

  1. 基础实现方案
    如果键不存在，SETNX 设置成功并返回 1，否则返回 0，以此保证互斥性。同时需要为键设置过期时间以防止死锁。

  2. 存在的问题与改进

    • 非原子性导致的死锁：如果客户端在执行完 SETNX 后，在执行 EXPIRE 命令前崩溃或发生网络中断，会导致锁永远不会过期，从而引发死锁。
    • 改进方案：通过增加 EX 参数（即 SET NX EX），保证设置值和过期时间在一个原子操作中完成。

  3. 误删锁与不可重入问题

    • 误删锁：如果客户端 A 获取锁后，业务逻辑执行时间超过了过期时间，锁会自动释放。此时客户端 B 获取到了锁，当客户端 A 执行完毕后再去执行删除锁的操作，就会把客户端 B 的锁给删掉。
    • 不可重入性：Redis 原始锁不支持同一个线程多次获取同一把锁。

  4. 引入 Lua 脚本与唯一标识
    为解决上述问题，引入了 Lua 脚本和 Value 唯一标识：

    • 唯一标识：在设置锁时，Value 不再是随机值，而是一个唯一的标识。
    • 原子解锁：在释放锁时，使用 Lua 脚本先判断当前锁的 Value 是否等于自己的唯一标识，只有相等时才执行删除。由于 Lua 脚本在 Redis 中是原子执行的，这保证了“判断”和“删除”过程的原子性。
    • 换成使用hset

使用 Lua 脚本和唯一标识可以解决误删锁和不可重入性的问题，但目前还存在一个隐患：如果业务执行时间超过了锁的过期时间，会导致互斥性失效。

  1. 场景示例：
    (a) 线程 A 获取锁后，执行任务需要 60 秒，但锁的默认过期时间设为 30 秒。
    (b) 30 秒后锁自动过期，此时线程 B 成功获取了该锁。
    (c) 线程 A 和线程 B 同时操作同一个资源，导致互斥性失效。

  2. 解决方案：看门狗（Watchdog）机制
    为了解决这个问题，可以采用守护进程（看门狗）机制：
    (a) 线程获取锁时，不再一次性设死一个较长的过期时间，而是先设定一个较短的默认过期时间（如 30 秒）。
    (b) 同时在后台启动一个定期续期的线程。
    (c) 只要业务线程还存活且持有锁，该后台线程就会不断地为锁延长过期时间。
    (d) 一旦业务执行完成，线程会主动释放锁。
    (e) 如果服务宕机，看门狗线程也会随之消失，锁最终会因达到过期时间而自然释放，避免死锁。

  3. 主从切换导致的锁丢失
    在集群或哨兵模式下，依然存在风险：
    (a) 客户端 A 在主节点获取锁后，主节点尚未将数据同步到从节点就宕机了。
    (b) 从节点升级为主节点，但其上并没有该锁的信息。
    (c) 客户端 B 可以在新的主节点上再次加锁，导致互斥性失效。

  4. 红锁（Redlock）解决方案
    为了解决主从切换导致的锁丢失问题，可以采用红锁方案。其核心逻辑如下：

    • 部署 N 个完全独立的 Redis 节点。
    • 客户端依次向这 N 个节点申请锁。
    • 只有在超过半数（N/2 + 1）的节点成功获取锁，且总耗时小于锁的有效期时，才视为加锁成功。
    • 释放锁时，向所有节点发送释放请求。

一般来讲，分布式锁有一个现成的方案叫 Redisson。它的机制主要通过以下几点来保证锁的可靠性：

  1. 使用哈希（Hash）结构
    用于保证锁的可重入性。

  2. 使用 Lua 脚本
    通过 Lua 脚本的原子性来防止误删。

  3. 增加看门狗（Watchdog）机制
    防止业务处理时间大于锁的过期时间，从而导致锁被提前释放。

6.2 经典问题

6.2.1 锁误删

原因：锁过期后别人拿到锁，旧线程再去删锁
解决：唯一标识 + Lua 原子删除

6.2.2 锁超时释放

原因：业务执行时间超过锁过期时间
解决：看门狗机制，后台自动续期

6.2.3 主从切换锁丢失

原因：Redis 主从异步复制，锁还没同步就故障切换
解决：可用 RedLock 缓解，但强一致场景更推荐 ZooKeeper / etcd

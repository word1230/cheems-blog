判题流程

用户提交题目

  1. 校验： 校验是否符合规定的语言，题目是否存在
  2. 设定题目状态为等待，判题信息为空，提交题目
  3. 执行判题服务
    1. 校验参数： 判断题目是否存在，提交信息是否存在，题目状态是否为等待
    2. 更新题目状态为判题中
    3. 获取输入用例，调用沙箱获取执行结果
    4. 根据沙箱执行结果和设定的case进行对错判断逻辑（策略模式）
      1. 对于c c++ python这种
        1. 先判断沙箱输出数量与预期数量是否相等
        2. 判断每一项输出于预期结果是否相等
        3. 判断题目内存 和时间限制
      2. 如果是java这类
        1. jvm启动安照10s计算
    5. 判断完成后返回判断结果
    6. 修改数据库的判题结果和判题信息
    7. 将判题结果返回

首先，用户将代码提交到后端后，后端会进行参数校验，比如校验编程语言是否是规定的类型，然后检查用户提交的题目是否存在，接着构建一个提交记录并存储到数据库中，设置这个提交记录的初始状态。

接下来是执行判题，这里先构建一个消息存储到消息发件箱表中。然后每五秒会有一个定时任务，从消息表中捞出最近尝试时间小于当前时间、最大重试次数小于最大重试次数，以及状态为待提交的消息，大概二十条，通过消费者发送出去，同时更新发件箱中消息的状态。

在消费者端，会调用判题服务，判题服务会调用代码沙箱。在代码沙箱中，先存储用户的代码并生成临时文件，然后进行编译，打开一个Docker容器，将代码复制进去执行，获取执行结果，然后删除临时文件。

拿到执行结果后，进行判断正误的服务，这里会从题目信息表中获取每道题的用例，将Docker容器输出的结果与用例进行比对，比如数量和每个用例的结果是否正确。判断完成后，再检查内存和时间消耗是否符合题目的要求，这样得到判题结果。

最后将判题结果更新到提交记录中，同时更新提交记录的状态，用户就可以在前端提交记录那里看到自己的提交记录。

你为什么选 Spring Boot + Docker + Redis + RabbitMQ 这一套？每个组件分别解决什么问题？

首先，Spring Boot是Java web开发的必备框架，

Docker是开发OJ系统所需的必要组件，当然你也可以使用原生方式在服务器本机安装Java环境来编译执行代码，但这样会有安全问题，比如用户在代码中写死循环或恶意代码，会占用服务器主线程或耗尽资源，虽然可以在代码中做限制，但终归不安全。所以使用Docker，容器与主机隔离，用户在容器中的行为不会影响主机，如果用户做了危险代码，只需销毁容器即可解决。

Redis主要是我在做项目过程中发现，数据库题目信息表存储的是JSON格式，导致主页获取题目列表较慢。基于这个问题，我目前使用Redis做缓存提高访问速度，之后考虑将用例移动到文件中，存储到对象存储中，通过动态读入来提高访问速度。

RabbitMQ用于判题的异步操作，用户提交代码后不用一直等待结果，可以继续做下一道题或查看当前题目的结果。

  1. 判题机架构 / 代码沙箱抽象

你说“自主设计判题机模块架构”，那你先讲一下判题模块的核心分层。

这个判题机架构主要分为两个部分，第一个是执行代码，也就是代码沙箱这一部分，第二个是判断代码执行结果与预设用例结果是否相同，也就是判断正确性的部分。

第一部分主要采用代码沙箱的形式，你可以采用原生的Java代码沙箱，也可以调用自己编写的代码上传，或者调用第三方写好的代码上传。为了先跑通流程，我写了一个示例代码上传。这里定义了一个代码上传工厂，工厂由配置决定具体调用第三方代码沙箱、远程代码沙箱还是本地代码沙箱，配置文件中进行配置。通过工厂模式，根据不同参数生成不同的代码生成实例。然后通过简单的动态代理给代码沙箱执行监控，增加执行日志。这个项目主要使用远程代码沙箱，也就是我自己编写的。

然后对于远程代码沙箱的话，这里主要有两种实现，第一种就是Java原生的实现，这种方式是在本地调用本地终端，然后传递参数去执行和编译Java文件，直接拿到对应的结果，当然这种方式有很大的缺陷和安全隐患，所以还增加了使用Docker容器进行的方式。同时，因为这两种方式只有运行代码的方式不一样，其他整个流程包括生成临时代码、编译代码、运行、获取结果、删除临时代码，这一整套流程是一样的，因此这里就采用了一个模板方法模式来减少重复的代码

第二部分是执行判题结果。对于C语言和Java语言的执行对比，Java语言因为要启动虚拟机等原因，执行速度更慢，因此在内存和执行时间的判断上需要有所不同。这里采用策略模式进行区分，在执行判题前先获取当前题目的语言，如果是Java就走Java的判题策略，如果是C语言就做C语言的判定策略，然后在判定策略里做对应的处理。

判题机的话，首先第一个是用户在提交代码到后端之后呢，对这个参数进行校验，然后同时呢，将生成一个提交记录，记录进行落库。

嗯，在这个部分呢会校验这个用户比如说用户的这个提交的题目是否存在语言是否符合预设，然后去生成一条提交记录并且设置这个提交记录的状态，然后去生成一条消息，然后存储到发件箱中。

第二部分的话是去发起这个调用运行代码运行层调用第三部分，他呢主要是负责获取到这个提交记录题目信息测试用例，然后将这些信息呢传给这个代码沙箱。

代码沙箱进行这个判题，第三部分呢就是这个代码沙箱部分，在这个部分呢主要负责将用户的代码呢转成这个应试文件，然后转成临时文件，然后进行编译运行，然后获取到运行结果，然后处理掉这个临时文件和生成的docker容器，这是代码平层。

然后呢是判题策略层，它呢主要是对于代码生成层它生成的返回的这个运行结果呢进行这个逐一判定，就是获取到预设的case，然后去与之进行一一对比。然后如果说结果正确的话，就会再去判断这个时间和这个内存是否符合题目要求，然后去更新这个提交状态。

RabbitMQ + Transactional Outbox

  • 你为什么不用“提交后直接发 MQ”，而是要引入 Outbox？

一个发件箱的目的是为了保证消息不会丢失，如果你不使用发件箱，直接调用生产者发送消息，比如生产者刚将消息发出，此时消息队列服务终止了，那么消息就会在这个过程中丢失，但是因为你已经修改了提交记录的状态，导致提交记录永远卡在这个状态，无法继续流转。

你使用了AutoBox的话，它首先引入AutoBox是因为它实际上是一个数据库，通过这个数据库的事务来实现同步的更改，因为你在更改状态后，需要同时把消息存储到发件箱中，以此保证状态修改与消息的状态是一致的，避免因消息队列无法正常使用而导致状态无法流转下去的问题。

为什么不直接在提交后发送 MQ，而是引入 Outbox（发件箱）模式？

首先，整体流程如下：

  1. 参数校验：用户从前端将代码提交到后端，后端先进行参数校验，包括题目 ID、语言是否为预设语言等。
  2. 提交记录：校验通过后，向 MySQL 提交一条记录，包括初始化判题状态（等待判题）和初始化判题信息。
  3. 生成消息：在同一个事务中生成一条消息，存入数据库的 Outbox 表（发件箱）中。
  4. 消息处理：
    (a) 由采集线程（或定时任务）从数据库中读取消息并发送到消息队列（MQ）。
    (b) 消费者基于线程池调用后端的判题服务。
  5. 执行判题：
    (a) 判题服务将提交记录中的状态改为“判题中”。
    (b) 调用代码沙箱获取执行结果。
    (c) 由判题服务依次对比执行结果与预设用例是否一一对应，从而给出最终判断结果并返回。

那么，为什么要使用 Outbox 模式呢？

如果直接在提交后发送 MQ，可能会遇到以下问题：

  1. 消息丢失：如果你在发送 MQ 时，消息队列正好中断或崩溃了，导致消息发送失败。
  2. 状态不一致：由于发送失败，你可能认为发送成功了（或者本地事务已提交），但实际上消费者并没有收到消息。这会导致提交记录的状态一直卡在“判题中”或“等待判题”，无法继续向下流转。

引入 Outbox 模式的核心目的就是为了保证消息不丢失。通过将消息和提交记录放在同一个数据库事务中进行提交，可以确保两者的原子性，从而彻底解决状态流转中断的问题。

如果你直接发送 MQ 而不用发送箱（Outbox）的话，就会导致以下两种情况：

  1. 提交记录入库成功，但消息发送失败；
  2. 消息发送成功，但提交记录入库失败。

这会导致消息提交的状态永远卡在“等待中”，无法继续向下流转，导致状态不完整。

这里引入 Outbox 模式，主要是为了保证“双写”的一致性，确保操作可以成功，同时保证消息不会丢失。

  • question_submit 和 mq_outbox 是怎么保证在一个事务里的？

这里的情况是：两个表都在同一个 MySQL 中，同时我在代码上加了 Spring 的事务注解，保证两个消息走的是同一个事务。这样要么同时成功，要么同时失败。

  • 如果数据库事务成功了，但 MQ 发送失败了，会发生什么？

当 MQ 发送失败后，系统会从数据库中读取并修改 Outbox 表（发件箱）中的数据状态：

  1. 更新重试信息：
    (a) 将重试次数加 1
    (b) 将下一次重试时间设置为 30 秒后
  2. 判断重试限制：
    系统会判断是否已达到最大重试次数。如果达到上限，则将该记录的重试时间改为空。

接下来，MQ 会由下一个定时任务（每 5 秒执行一次）进行补偿处理。该任务会再次从 Outbox 中读取符合以下条件的记录：

  • 重试次数不超过最大重试次数
  • 重试时间小于当前时间
  • 按照 ID 顺序筛选（例如每次选出 20 条）
  • 状态处于等待和失败

读取到这些记录后，系统会重新将其发送给消费者进行消费。

  • Outbox 补偿发布是怎么做的？扫描频率为什么这么定？

我这里采用的是定时任务的方式去扫描 Outbox 表，具体的处理逻辑如下：

  1. 筛选逻辑
    从中筛选出状态为“等待”和“失败”的记录，且满足以下条件：
    (a) 重试时间小于当前时间
    (b) 重试次数小于最大重试次数
  2. 数据排序与提取
    按照 ID 进行排序，每次筛选出 20 条记录。
  3. 消息发送
    将筛选出的记录发送给消费者进行消费。

关于扫描频率，设置是每 5 秒钟进行一次。
失败的话会等待 30 秒后重试。

关于 5 秒的扫描频率，这是一个折中的方案。因为这属于一种判定服务（Judge Service），不需要极高的实时性，但也不能太慢。设置 5 秒是为了平衡数据库压力与业务需求。

如果后续业务量增长，我会考虑将目前的“扫表”方式，替换为通过 Binlog 驱动或者 CDC（Change Data Capture）模式。

  • 你这个方案保证的是 at-least-once、at-most-once 还是 exactly-once？

这套方案保证的是 at-least-once，也就是至少投递一次，不保证绝对不重复。
我是刻意偏向“不丢消息”这一侧的，因为在分布式场景里，端到端 exactly-once 成本很高，通常工程上更现实的做法是 at-least-once + 幂等消费。

这里保证每个消息至少投递一次，但它会出现重复投递的情况。

因为我这里处理的是判题逻辑，判题是绝对不能丢消息的。虽然用户一直点击，加上前端也加了防抖，不会触发第二次提交。但如果这次提交失败了，给用户的体验会比较差，所以这里实现的是“至少一次”（At-least-once）投递。

这里会出现重复投递的情况。如果消息发布或投递失败，系统会尝试修改数据库中 Outbox 表的消息状态。但如果修改数据库这一步失败了，导致消息状态没能成功更新，系统就会继续尝试重发，甚至可能超过最大重试次数。另一种情况是，虽然投递成功了，但修改数据库状态时失败，同样会导致系统再次发送，从而产生重复消息。

针对这个问题，我在后续的判题逻辑中做了处理：

  1. 状态校验
    在执行判题前，系统会先判断这条消息的状态。如果消息处于“判题中”或“已判题完成”，系统会直接跳过该消息。

  2. 流程回馈
    跳过后，系统不再重复执行判题逻辑，而是直接进入给消费者回馈的流程。

通过这种方式，从业务层面上阻止了重复判题的可能性。

  • 如果消息重复投递了，你怎么保证判题不会重复执行？
    当前项目的思路是靠业务状态机兜底。判题记录一开始是 WAITING，消费时先检查状态，不是 WAITING 就直接跳过；开始执行前把状态改成 RUNNING，完成后改成 SUCCEED 或 FAILED。这样大多数重复消息都会被挡住。
    但我也会诚实说，这个实现现在是“有幂等意识”，还不是最强版本。更稳妥的做法应该是把“WAITING -> RUNNING”改成带条件的 CAS 更新，比如 where id = ? and status = WAITING，这样并发重复消息也只能有一个线程抢到执行权。

  • 你用了手动 ACK，那 ACK 的时机是什么？如果判题中途异常，你怎么处理？

我这里是手动 ACK，只有在 judgeService.doJudge() 真正执行成功，并且判题结果已经落库以后，才 ACK。
如果判题中途异常，我不会 ACK，而是 basicReject(requeue=false)，让消息进入死信队列。同时业务侧会把这次提交状态更新成 FAILED，并记录错误信息，避免消息失败了但业务状态一直卡在处理中。

  • 失败消息进死信队列之后，后续怎么消费、告警或人工处理？

当前项目已经把 DLQ 配好了，但还没有把 DLQ 的自动化运维链路补完整。现在更像是一个兜底沉淀区，方便人工排查。
如果上生产，我会补三件事：第一，给 DLQ 单独做监控和告警；第二，提供一个人工回放工具，可以把修复后的消息重新投递；第三，把死信原因、重试次数、traceId 打通到日志和监控系统里，便于定位问题。

  • 你有没有做 publisher confirm？
    当前这个版本还没有把 publisher confirm 和 return callback 接上，这一点我会直接说明。现在是 convertAndSend() 不抛异常，就把 outbox 标成 SENT，这在工程上是有风险的。

  • 为什么 convertAndSend() 成功返回就把 outbox 标成 SENT，这里会不会有一致性风险？

会，这里确实有一致性风险。因为 convertAndSend() 成功返回，只能说明客户端这次发送调用没有抛异常，不等于 Broker 一定已经持久化成功，也不等于消息一定路由到了目标队列。
更稳妥的做法应该是：发送时带上 correlationData=outboxId，开启 publisher confirm。只有收到 Broker 的 confirm ack 后，才把 outbox 标成 SENT；如果收到 nack，或者消息不可路由被 return，就把 outbox 标成 FAILED 并记录原因，后面继续补偿。
所以如果面试官问到这里，我会说：当前方案已经解决了“业务事务和消息落地”的大问题，但在“发布确认”这一层还可以继续增强，这也是我下一步会优化的点。

  1. 并发控制

这里的并发控制主要分为三层：

  1. RabbitMQ 消息拉取限制
    RabbitMQ 负责承接任务，但不代表任务一到就马上执行。为了避免消费者并发数随着流量无限放大，需要对消费者处理消息的条数进行限制，设置 prefetch 为一次只拉取 1 到 5 条。这样可以让消息堆积在 MQ 中，而不是直接去请求创建过多的 Docker 容器。

  2. 线程池管控
    第二层是使用一个固定大小的线程池进行管控。不要让每条消息都直接进入真实的判题执行，而是在前面加一层有界的执行池。通过固定大小的线程池，当队列满了之后不再接受新的执行，让消息继续留在 MQ 里或者返回系统繁忙。

  3. Sandbox 代码层信号量控制
    第三层是在 Sandbox 的代码层面做了一个 Semaphore（信号量）的限流。直接使用信号量对执行过程进行限制，确保并发量在可控范围内。

实习经历

第一部分：你的自适应学习计划是如何实现的？请总体描述一下

首先，整体计划分为四个阶段。核心思路是建立一套学习路径，并根据不同的阶段采取相应的策略为用户分配题目。

具体实现分为以下几个模块：

  1. 学习路径与知识点构建
    基于图数据库建立一个“考点图谱”，将所有知识点组织成类似“树”的结构。
    (a) 提取路径节点：从学习路径中抽取知识点（节点），按照一定规则进行排列。
    (b) 关联资源：每个知识点下都关联了相应的题目和讲解视频。

  2. 阶段化题目分配
    整个计划包含四个阶段：理论学习、题目模块、实战和冲刺。
    (a) 系统会根据用户所处的阶段，应用不同的规则和策略来分配题目。
    (b) 系统会预先给出用户一周的学习计划，明确每天需要掌握的内容。

  3. 动态调整机制
    学习计划是动态变化的。如果用户某天学的比较多，或者当天没有学习，系统会根据用户的实时动作进行动态调整。

  4. 评估机制与指标
    通过多个维度的指标对用户的学习进度进行判断：
    (a) 周目标：例如完成周内所有任务，或至少完成 80%。
    (b) 阶段任务：设定预测分达标要求。
    (c) 量化指标：包括总学习时长、做题量以及任务完成比例。
    (d) 进度状态：判断计划是“崩溃”、“提前”还是达到了“最小要求”。

我主要负责的部分包括：考点路径的计算、阶段目标的计算，以及学习进度评估中的状态计算。

其中，考点路径的计算主要是基于我们之前的考点图谱。我们利用图数据库形成了一个类似于树形的考点图谱，将所有的知识点都包含在内，构建出一个层级结构。

考点路径的具体形成过程如下：

  1. 获取根节点：
    从根节点开始向下递归，获取所有的子节点。

  2. 排序与价值计算：
    在递归过程中，需要对节点进行排序。排序是根据“考点价值”来衡量的。
    考点价值是根据产品的预设公式，综合考点的分数、难度以及考评情况计算出来的。

  3. 资源关联过滤：
    为了保证路径的有效性，如果某个节点没有关联任何学习资源，系统就不会将其记录到考点链中，而是直接将其剔除。

  4. 链表构建：
    通过上述步骤，从底层向上层节点逐级连接，最终构建出一个完整的链表结构。

  5. 用户偏好过滤：
    在链表构建完成后，还需要根据用户的偏好进行过滤。
    (a) 用户偏好（如希望先学什么、不想学什么）以数据表或数字图链的形式存储在数据库中。
    (b) 系统读取这些偏好数据，从已有的考点链中过滤掉不符合要求的内容。

最后，系统保留用户需要的考点路径并进行返回。这就是考点路径计算的核心逻辑。

学习计划的评估逻辑

关于学习计划的评估，其核心在于计算目标是否达成。目标主要分为总目标和阶段目标：

  1. 目标达成标准
    主要考察以下几个维度：
    (a) 是否达到预测分的标准
    (b) 学习时长是否足够
    (c) 完成的题目数量是否达标

    总目标和各个阶段目标都有各自预设的目标量。

  2. 状态评估逻辑
    评估是分阶段进行的，主要分为“周评估”和“阶段评估”，系统会根据计算结果给出相应的状态：

    • 周评估（已完成/进行中/无法完成）：
      (a) 已完成： 如果今天在周内且所有任务已完成，或者已经过了本周截止日且所有任务均已完成，状态为“已完成”。
      (b) 进行中： 任务按计划推进，完全没有问题。
      (c) 无法完成： 如果今天虽然在周内，但按照每周最大学习时长计算，已经无法完成剩余任务，则状态判定为“崩溃”（即无法完成）。

    • 阶段评估：
      (a) 如果用户处在阶段中，但阶段考点路径里的所有考点都已学完，视为提前完成。
      (b) 如果在当前阶段内，模拟任务按照最大学习时长也无法完成，状态同样判定为“崩溃”。

  3. 数据计算与技术实现
    这里涉及两种计算法（周计算和阶段计算），采用的是从底层向上汇总数据的思路：

    • 数据维度： 按照“天 → 周 → 阶段 → 整体”的维度层层递进。系统会从每天的节点中，将学习时长等属性累加起来，再按照预设规则进行判断。
    • 事件机制： 采用基于事件的机制。当用户进入系统时，首先进行周判断。
    • 调用逻辑： 周判断完成后，会同时进行周计算和阶段计算。系统会优先判断阶段状态，如果阶段已经处于“崩溃”状态，则直接调用相应逻辑；如果阶段没有崩溃，则继续正常的调用流程。

    (b) 科目信息：该题目所属的科目。
    (c) 难度等级：题目的难易程度。
    (d) 答题状态：用户回答正确或错误的情况。
  3. 模式匹配：
    根据解析出的不同参数，程序会切换到不同的模式（如 Tool, Agent, OSS, Claude 等）来获取预测结果，并最终将其填入 Excel。

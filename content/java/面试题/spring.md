## 4 aop

什么是 AOP？它解决了什么问题？  
AOP（面向切面编程）主要解决的是在开发场景中，代码里会散落大量与核心业务逻辑无关的代码，例如记录日志、鉴权等。这些功能与核心业务不是强相关，但又必须要写，且往往需要多次重复编写。

1. AOP 的优势  
    (a) 能够将这些横切关注点（如日志、事务）与核心业务逻辑进行解耦  
    (b) 将这些逻辑集中在切面（Aspect）中进行管理，方便维护，避免了代码的冗余
    
2. AOP 的实现原理  
    AOP 主要是基于代理模式来实现的。在 Java（以 Spring 为例）中，动态代理主要分为两种：  
    (a) JDK 动态代理：基于接口实现  
    (b) CGLIB 动态代理：基于继承（子类）实现  
    当调用被增强的方法时，实际上调用的是代理对象，代理对象会在目标方法执行前后插入通知逻辑。
    Spring 默认优先使用 JDK 动态代理；如果目标对象没有实现接口，或者强制指定 `proxyTargetClass=true`，则使用 CGLIB。
    
3. AOP 失效的场景：同类内部自调用  
    AOP 有一个典型的失效场景，即在同一个类内部进行方法自调用时。  
    失效的原因在于：当从外部调用时，调用的是 Spring 容器管理的代理对象，因此能触发增强逻辑；但在同类中直接调用（如 `this.method()`），调用的是目标对象本身而非代理对象，没有经过代理层的拦截，导致 AOP 逻辑无法生效。

AOP 是面向切面编程，主要用于将日志、事务、权限校验等横切关注点从核心业务逻辑中抽离出来，实现解耦，减少重复代码，并提高可维护性。  
在 Spring 中，AOP 主要是基于动态代理实现的。若目标对象实现了接口，通常使用 JDK 动态代理；若没有实现接口，或者配置了 `proxyTargetClass=true`，则使用 CGLIB 动态代理。  
当调用被增强的方法时，实际上是通过代理对象进行调用，代理对象会在目标方法执行前后插入额外逻辑。  
需要注意的是，Spring AOP 基于代理机制，因此如果在同一个类内部通过 `this.method()` 进行自调用，调用不会经过代理对象，切面逻辑就可能失效。这也是 `@Transactional` 等注解常见的失效原因之一。



## 5 事务

讲一讲 Spring 的事务管理：

### 5.1 Spring 支持哪些事务管理方式
Spring 支持两种事务管理方式：

1. 编程式事务
   你可以显式地在代码中编写事务的控制机制。
2. 声明式事务
   你只需要声明需要事务，具体的开启、提交和回滚操作均交由 Spring 自己来完成。

在实际开发中，最常用的是声明式事务配合 @Transactional 注解。


### 5.2 @Transactional 注解的工作原理


@Transactional 注解是基于 AOP 实现的，其核心工作流程如下：

1. 代理对象的调用
   当一个类或方法被标注为使用事务时，系统会调用代理对象。在调用过程中，代理对象会首先读取事务的属性配置，包括：
   (a) 传播行为
   (b) 隔离级别
   (c) 超时时间
   (d) 回滚触发条件
   这些元数据主要来源于 @Transactional 注解。

2. 事务管理与执行
   通过 TransactionManager 开启事务后，执行目标对象对应的方法。

3. 结果处理
   系统根据方法的执行结果进行判断：
   (a) 若执行成功，则提交事务
   (b) 若出现异常，则根据配置决定是否回滚

该机制主要依赖于 AOP 和代理模式两种机制来实现。


### 5.3 Spring 事务的传播行为


事务的传播机制主要解决的是：当一个事务方法去调用另一个事务方法时，事务应该如何传播。

系统共定义了 7 种传播行为：

1. REQUIRED（默认方法）
   当有事务时就加入；如果没有事务，就新建一个事务。

2. REQUIRES_NEW
   当执行到该方法时，不管当前有没有事务，都重新开启一个事务。如果外层已经有了事务，则先将外层事务挂起，直到新开启的事务方法执行完成后，再恢复外层事务。
   (a) 这种情况下，哪怕主事务失效，当前事务依然会被提交。
   (b) 主要应用于日志记录、审计等功能，它与外部事务相互独立。

3. SUPPORTS
   如果当前有事务，就加入；如果没有事务，可以以非事务方式执行。

4. NOT_SUPPORTED
   始终以非事务方式执行。如果当前存在事务，则将其挂起。

5. MANDATORY
   必须在已有事务中执行。如果当前没有事务，直接抛出异常。

6. NEVER
   必须在无事务环境下执行。如果当前有事务，直接抛出异常。

7. NESTED
   如果当前有事务，就在事务内部创建一个嵌套事务；如果没有事务，则按默认方式新建一个事务。

在大多数情况下，我们都会选择默认方式。但在某些特定场景下（例如希望局部失败而不影响主流程），可以根据需求选择 REQUIRES_NEW 或 NESTED 模式。



4. Spring 事务隔离级别

事务隔离级别解决的是多个并发事务同时操作数据时，数据可见性的问题。在并发情况下，可能会产生脏读（Dirty Read）、不可重复读（Non-repeatable Read）和幻读（Phantom Read）等问题。
### 5.4 Spring 事务的隔离级别

Spring 支持以下 5 种隔离级别：

1. 默认级别 (DEFAULT)
   使用底层数据库默认的隔离级别。
   (a) MySQL 的默认级别是可重复读（REPEATABLE READ）
   (b) Oracle 的默认级别是读已提交（READ COMMITTED）

2. 读未提交 (READ UNCOMMITTED)
   这是最低的隔离级别，可能导致脏读、不可重复读和幻读。

3. 读已提交 (READ COMMITTED)
   可以解决脏读问题，但仍可能导致不可重复读和幻读。

4. 可重复读 (REPEATABLE READ)
   可以解决脏读和不可重复读问题。

5. 串行化 (SERIALIZABLE)
   这是最高的隔离级别，通过强制事务排序，可以解决脏读、不可重复读和幻读，但性能最差。
### 5.5 在什么情况下 @Transactional 会失效


会导致 @Transactional 注解失效的原因：

1. 方法不是通过 Spring 代理调用的
   最典型的情况是类内部的方法自调用。在这种情况下，类内部会直接调用对象本身的方法，而不是经过代理对象。由于 Spring 事务是基于 AOP 和代理机制实现的，这种非代理调用会导致事务失效。

2. 对象不被 Spring 管理
   如果对象本身不是一个由 Spring 管理的 Bean（例如是你自己通过 new 关键字创建出来的对象），它同样不会被代理，AOP 也就无法生效，因此事务不会起作用。

3. 异常类型不符合默认的回滚规则
   Spring 默认的事务回滚规则是只在遇到 RuntimeException 和 Error 时才进行回滚。如果程序抛出的是编译时异常（Checked Exception），默认情况下它是不会回滚的。

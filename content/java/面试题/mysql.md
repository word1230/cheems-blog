## 1 数据类型选型


### 1.1 MySQL 中 char 和 varchar 的区别？开发中如何选择

char 和 varchar 的主要区别可以从以下几个方面来看：

1. 存储方式
   (a) char 是固定长度存储，申请多少空间就会占用多少空间.没用的会用空格补齐
   (b) varchar 是可变长度存储，虽然申请了空间，但它会按照你实际使用的长度来分配空间.再多1到2个字符来存储长度
2. 存储限制
   (a) char 的最长长度只能到 255
   (b) varchar 的最长长度可以达到 65535
3. 性能表现
   由于 varchar 是变长的，在处理时性能会稍微低一点。但在日常开发中，这种性能差异通常不会产生太明显的影响。

具体选择建议：
在 90% 的场景下都建议使用 varchar。除非你的业务字段是绝对的固定长度（例如身份证号、电话号码或邮政编码等），此时才会考虑使用 char。



### 1.2 MySQL 数值类型、日期类型的核心选型规则是什么

MySQL 中数值类型的选择规则如下：

1. 根据数据类型选择
   (a) 纯整数：选择 integer 相关类型
   (b) 非精确浮点数（有小数但不要求绝对精确）：可以使用 float 或 double
   (c) 精确小数（要求绝对精确）：必须使用 decimal 类型

2. 根据取值范围选择
   查看数据的最大值和最小值范围，在保证能正常容纳的前提下，选择占用空间最小的类型，从而优化存储性能。




MySQL 中日期类型的选择，首先要看你需要存储的字段所要求的精度和场景：



4. 基础日期与时间类型
   (a) 如果只需要存日期，使用 Date 类型
   (b) 如果只需要存时间，使用 Time 类型
   (c) 如果需要日期加时间，使用 DateTime 类型

5. 时区转换与自动更新场景（Timestamp）
   Timestamp 类型与时区有关，MySQL 内部会进行自动转换，非常适合跨时区的场景。在一些常见场景中，例如创建时间和更新时间字段，经常使用 Timestamp。

6. 业务逻辑场景
   (a) 对于订单下单时间等业务场景，通常使用 DateTime
   (b) 如果需要记录时长或时间间隔，可以考虑计算 TimestampDiff

总之，应根据数据的实际业务含义和是否需要时区敏感性来做出选择。


## 2 存储引擎基础


### 2.1 InnoDB 和 MyISAM 存储引擎的核心区别，以及适用场景

MySQL 的存储引擎主要有 InnoDB、MyISAM 和 Memory。其中最常用的是 InnoDB，但在某些场景下也会使用 MyISAM。

InnoDB 和 MyISAM 的核心区别如下：

1. InnoDB 存储引擎
   (a) 支持行级锁（行锁）
   (b) 支持事务处理
   (c) 拥有崩溃日志（Redo Log），支持崩溃后的数据恢复
   (d) 索引结构采用 B+ 树，属于聚簇索引

2. MyISAM 存储引擎
   (a) 只支持表级锁（表锁），不支持行锁
   (b) 不支持事务
   (c) 没有崩溃恢复机制
   (d) 索引为非聚簇索引

在绝大部分实际场景中，都推荐使用 InnoDB。只有在数据几乎不更新，或者是一些非常陈旧的特定场景中，才会考虑使用 MyISAM。


Memory 存储引擎的特点：
1. 它的索引类型采用的是 Hash 索引，底层是哈希表结构。
2. 数据存储在内存中。
3. 它几乎只在一些临时开发或临时测试的场景中会被用到。




### 2.2 MySQL 插件式存储引擎架构的核心特性是什么


MySQL 的**插件式存储引擎架构（Pluggable Storage Engine Architecture）**是其区别于其他关系型数据库的核心特性。这种架构将**查询处理（SQL Layer）**与**数据存储（Storage Layer）**解耦，允许用户根据业务需求为不同的表选择不同的存储方式。

### 2.3 核心原理

在 MySQL 中，数据库服务器被分为两层：

- **上层（Server 层）：** 负责连接管理、查询解析、SQL 优化、缓存以及所有内置函数。这一层不直接接触物理文件。
- **下层（存储引擎层）：** 负责数据的存储和提取。Server 层通过一套标准的 **存储引擎 API** 与下层通信。只要符合接口规范，任何机构或个人都可以开发自己的存储引擎。

### 2.4 常见存储引擎对比

不同的引擎有不同的特性，最常用的是以下两种：

|特性|InnoDB|MyISAM|
|---|---|---|
|**事务支持**|**支持** (ACID)|不支持|
|**锁定机制**|**行级锁** (并发度高)|表级锁 (并发度低)|
|**外键**|**支持**|不支持|
|**崩溃恢复**|具有 Redo Log，支持自动恢复|不支持|
|**适用场景**|绝大多数通用业务（默认引擎）|只读或大量插入、较少更新的场景|

### 2.5 该架构的优势

- **灵活性：** 你可以针对不同的表使用不同的引擎。例如：核心订单表用支持事务的 **InnoDB**，临时统计数据或日志表可以用压缩率极高的 **Archive** 引擎。
- **易扩展性：** 开发者可以根据特殊硬件（如内存数据库、分布式存储）定制专用的存储引擎，而无需修改 MySQL 核心代码。
- **优化性能：** 通过选择合适的引擎（如仅在内存中运行的 **Memory** 引擎），可以极大地提升特定场景下的读写速度。

### 2.6 如何查看与使用

- **查看支持的引擎：** `SHOW ENGINES;`
- **指定引擎建表：**
    
    ```
    CREATE TABLE my_table (id INT) ENGINE = InnoDB;
    ```
    

**总结：** 这种架构就像给汽车（MySQL）设计了一个通用的底盘，用户可以根据路况（业务需求）随意更换不同的引擎（InnoDB, MyISAM 等），而方向盘和仪表盘（SQL 语法和接口）保持不变。



MySQL 的插件式存储引擎架构，是指将 MySQL 服务器分为两层：

1. Server 层
   它主要负责 SQL 的解析、执行等操作。
2. 存储引擎层
   它负责数据的落盘操作。

这种架构将两层进行解耦，它们之间通过一套标准的存储引擎 API 接口进行通信。这样做的好处在于：

1. 灵活性极高
   将操作数据的方式与数据落盘的动作解耦开。你可以灵活地使用多种存储引擎，甚至可以在同一个数据库中，针对不同的表使用不同的存储引擎。
2. 扩展性强
   你可以根据硬件环境去定制自己的存储引擎。












## 3 索引



### 3.1 什么是主键、外键、唯一索引、普通索引？核心区别是什么

1. 主键（Primary Key）
   MySQL 中表数据的唯一标识。它是全表唯一且不可重复的，并且不允许为空。主键本质上是“约束 + 索引”，既要保证数据的非空性，也要保证其唯一性。

2. 外键（Foreign Key）
   建立当前表与另一个表之间的联系。外键允许重复，其本质是一种约束，用于维护表与表之间的数据一致性。

3. 唯一索引（Unique Index）
   要求当前列在表中保持数据唯一，但与主键不同的是，它允许数据为空。唯一索引也是“索引 + 约束”的结合，在保证唯一性的同时进行索引加速。

4. 普通索引（Normal Index）
   没有任何约束作用，纯粹是为了加速查询。


### 3.2 索引是什么

索引是存储在磁盘中的一种数据结构。在 MySQL 的 InnoDB 架构中，或者说在 InnoDB 存储引擎里，它通常表现为 B+ 树。

它就像是你书的目录一样，主要作用是为了加速查询。
除了加速查询之外，它还可以降低磁盘 IO 率。

如果没有索引，你要查询一个数据，就需要从所有存储的数据中一页一页地去找。这样的话，磁盘 IO 就会非常大，速度也会非常慢。

索引的作用主要体现在以下几点：
1. 数据排序：它是将你的数据按照顺序进行排列，形成一棵 B+ 树。
2. 高效查找：查询时只需要在 B+ 树上进行查找，使用二分搜索定位到叶子节点，就可以拿到数据。
3. 性能提升：通常磁盘 IO 只需要 2-3 次，查询速度非常快。



### 3.3 MySQL 为什么使用 B+ 树作为索引的数据结构？

B+ 树的层级比较低，通常只有 3-4 层。而三层 B+ 树大概可以存储 2000 万左右的数据，这意味着在磁盘 IO 只有 2 到 3 次的情况下，就可以查询到这两千万条数据。

然后叶子节点之间是通过双向链表进行连接，使得其天然支持高效的范围查询。




为什么不选择其他的数据结构作为索引的数据结构？首先，可选的方案包括二叉搜索树、红黑树、哈希表以及 B 树。

1. 二叉搜索树与红黑树
   它们的问题在于树高太高。如果层级比较高，磁盘 I/O 次数就会非常大。

2. 哈希表
   由于它是通过哈希键值对进行存储，所以只支持精确查询，不支持范围查询。

3. B 树
   B 树的问题在于所有的节点都存储完整的数据，这会导致查询效率较低，且树高也相对较高。

4. B+ 树
   (a) 特点是只有叶子节点存储所有数据，非叶子节点仅存储键值和指针。
   (b) 其中的键值主要是给出子树所包含的数据范围，通过二分查找就可以快速定位到数据。
   (c) 另一个特点是它的叶子节点通过双向链表进行连接，因此支持高效的范围查询。



### 3.4 索引的分类,聚簇索引和非聚簇索引

1. 按照数据结构划分
   (a) B+ 树索引
       这是 MySQL 最常用的索引类型。其非叶子节点存储键值和指针，而叶子节点存储所有数据，并形成双向链表。
   (b) 哈希索引
       底层是哈希表，仅适合等值查询。
   (c) 全文索引
       类似于搜索引擎，用于查找文中的关键词。现在一般采用 Elasticsearch 替代。

2. 按照物理存储划分
   (a) 聚簇索引
       数据和索引绑定在一起。在 B+ 树的叶子节点中，直接存放了这一行的完整数据。其特点是每张表只能有一个聚簇索引。在 InnoDB 存储引擎中，主键索引就是聚簇索引。
   (b) 非聚簇索引
       B+ 树的叶子节点存储的是索引列和对应主键的值。其特点是每张表可以拥有多个非聚簇索引。

3. 按照逻辑功能划分
   可以分为主键索引、唯一索引和普通索引。

### 3.5 回表与覆盖索引是什么？

首先，一个正常的查询过程如下：

1. 聚簇索引查询
   如果你的 where 条件中包含主键，MySQL 判断你是根据主键进行查询，那么它会找到聚簇索引（B+ 树）。在非叶子节点上通过二分查找去找到叶子节点。此时，叶子节点中存储的是整行的完整数据，直接从中获取你需要的数据并返回即可。

2. 非聚簇索引查询与回表
   如果你查询的条件是使用非聚簇索引，系统判断后会先去对应的非聚簇索引 B+ 树中寻找。同样通过二分查找找到叶子节点，但非聚簇索引的叶子节点中仅存储了当前索引列和主键值。
   
   如果你需要的数据不只有索引列和主键，就会触发“回表”：也就是说，系统会带着从非聚簇索引中找到的主键，再次回到聚簇索引的 B+ 树中寻找一遍，以获取完整的数据。

3. 覆盖索引
   覆盖索引的意思是：你查询所需的所有数据，正好就是索引列和主键值。在这种情况下，你在非聚簇索引的 B+ 树中就能直接查到所需数据并返回，而不需要触发回表操作。

### 3.6 联合索引与 最左前缀法则
#### 3.6.1 最左匹配原则

1. **什么是最左匹配原则**
   最左匹配原则是指：当你想要使用联合索引进行查询时，查询条件必须按照联合索引的顺序进行排列，否则会导致联合索引失效。

2. **核心原理**
   在创建联合索引时（例如按照 A、B、C 的顺序），MySQL 会先将数据按照 A 列进行排序（如字典序）。当 A 的数值相同时，再按照 B 的大小进行排列；如果 B 也相同，则按照 C 排列。
   
   这种机制保证了数据在索引中的整体有序性：
   - 如果不按照最左匹配原则（例如查询条件是 `CBA`），系统需要先查找 C。
   - 但由于 C 只有在 B 相同时才是有序的，对于整个索引来说 C 是乱序的。
   - 乱序导致无法使用二分查找，从而使索引失效。

#### 3.6.2 模糊查询（Like）的匹配规则

Like 模糊查询只支持“左匹配”，即 `al%` 这种形式：
1. **原理：** 这与上述排序原理一致。只有给定左半部分的真实数据，MySQL 才能按照字典序进行匹配。
2. **失效场景：** 如果使用 `%ce`（以 CE 结尾），MySQL 会匹配所有以 CE 结尾的数据。由于这些数据在索引中的顺序并不是排好的，会导致索引失效。
3. **结论：** 模糊查询只能在右半边使用通配符，左半边必须是真实的固定数据。

#### 3.6.3 范围查询对联合索引的影响

使用大于（`>`）等范围查询会截断联合索引：
1. **原因：** 使用范围查询后，你拿到的是一个范围内的数据（例如 A 在某个范围内）。
2. **失效机制：** 在这个 A 的范围内，B 列的数据并不是从大到小排列的。只有当 A 的值完全相同时，B 才有序。
3. **结果：** 由于该范围内包含了不同的 A 值，导致其后的索引列（如 B、C）无法再利用索引的有序性，从而造成索引截断。

#### 3.6.4 索引下推
- **没有 ICP 的情况**：联合索引 `INDEX(name, age)`，查询 `SELECT * FROM table WHERE name LIKE '张%' AND age = 20`。MySQL 会通过索引找到所有姓张的人的主键，然后**回表**去聚簇索引中取出完整数据，最后在 Server 层过滤出 age=20 的人。
- **有 ICP 的情况**：在索引遍历过程中，**直接在存储引擎层**对 `age = 20` 进行判断。如果不满足，直接跳过，不需要回表。大大减少了回表次数。


### 3.7 常见的索引失效的场景

由于索引实际上是去构建了一棵 B+ 树，如果你对这棵 B+ 树的数据做了修改，就相当于整棵 B+ 树都要进行修改。此时就会导致索引失效，即 SQL 优化器会认为使用索引还不如不使用索引查得快，因此索引就失效了。

具体的失效条件包括：
1. 对索引列使用了运算或函数
2. 触发了一些隐式转换
3. 违反了最左匹配原则




## 4 事务

### 4.1 什么是事务？



事务是指在进行数据库操作时的最小逻辑单元。一个事务中包含了一组操作数据库的语句，它要求这一组操作要么全部成功，要么全部失败，不允许出现中间状态。

举个例子：
比如说 A 给 B 转账了 100 元，它实际上是分为两个步骤：
1. A 从自己的账户中扣除 100 元
2. B 的账户增加 100 元

如果步骤一成功了，但是步骤二失败了，就会导致 A 的钱扣除了，但 B 也没有收到这笔钱。而事务就是保证这两个步骤作为一个整体来执行的。



### 4.2 事务的四个特性

主要包括：
1. 原子性
2. 一致性
3. 隔离性
4. 持久性

5. 原子性
   是指一个事务中的操作要么都成功，要么都失败，不存在一个成功而另一个不成功的情况。

6. 一致性
   是原子性、隔离性、持久性的最终目的。即数据的状态要从一个合法状态转换到另一个合法状态。

7. 隔离性
   是指一个事务的执行不会影响到另一个事务，事务与事务之间是相互隔离的。

8. 持久性
   是指事务一旦提交，数据的改变就是永久的，哪怕数据库遭遇断电或宕机。

### 4.3 事务的并发问题(脏读、幻读、不可重复读)(为什么需要隔离性)

为什么需要隔离性？

如果事务与事务之间不隔离，就会出现脏读、幻读、不可重复读的情况。

1. 脏读
   是指事务 A 读取到了事务 B 尚未提交的数据。如果事务 B 修改了数据但没有提交，随后发生了回滚，那么此时事务 A 读取到的数据就是不存在的脏数据。

2. 不可重复读
   是指事务 A 在同一个事务中连续读取了两次数据，但这两次的数据结果不相同。这是因为在事务 A 第一次读完之后，事务 B 修改了该数据并提交，导致事务 A 在第二次查询时，发现两次读取到的数据不一致。

3. 幻读
   是指事务 A 执行相同的范围查询，但两次得到的行数不一致。因为在两次查询之间，事务 B 插入了一行新数据并提交了事务，导致两次查询的结果集行数发生了变化。


为了解决这三个问题，引出了事务的四种隔离级别，分别是读未提交、读已提交、可重复读和串行化：

1. 读未提交（Read Uncommitted）
   (a) 基本上没有隔离性，连脏读都防不住。

2. 读已提交（Read Committed）
   (a) 可以防止脏读的发生，但不能防止不可重复读和幻读。
   (b) 这是 Oracle 的默认级别。

3. 可重复读（Repeatable Read）
   (a) 可以防止脏读和不可重复读，但不能防止幻读。
   (b) 这是 MySQL 中 InnoDB 存储引擎的默认级别。

4. 串行化（Serializable）
   (a) 通过加锁实现，相当于单线程执行。
   (b) 可以防止脏读、不可重复读和幻读。
   (c) 它的性能也是最低的。
### 4.4 MySQL 实现事务的底层原理。(MySQL 是如何实现这个事务的四个特性？)

#### 4.4.1 原子性
主要是依靠 undo log。undo log 是一个反向日志文件，它记录的是你所执行操作的反向操作。

当你在这个事务中执行一个更新操作（例如更新 ID，使金额增加 5），那么在 undo log 里就会记录金额减少 5 的反向操作。而当事务要回滚时，系统会读取 undo log 并且执行其中的操作，从而实现回滚，保证原子性。


它的底层是一个 Undo Log 版本链。在 InnoDB 的每行数据中，都有两个隐藏的列，分别是：
1. 记录最后一次修改该行的事务 ID
2. 回滚指针（指向该行数据的上一个版本）

每次修改一行数据时，它都不会直接覆盖旧的数据，而是通过回滚指针将旧数据串联起来，形成一条版本链。这条链的源头就存在于 Undo Log 中。


同时，Undo Log 也用于多版本并发控制。


#### 4.4.2 持久性

主要依靠 redo log 实现。redo log 是一种物理日志，记录的是在数据页的偏移量上做了哪些物理修改。它采用固定的循环使用机制。

其工作机制如下：
1. 修改数据时，先在内存的缓存池（Buffer Pool）中进行修改。
2. 同时，将该修改操作的物理记录写入 redo log buffer（缓存）中。
3. 当事务提交后，将 redo log buffer 中的内容刷入磁盘上的 redo log 文件。
4. 真正的数据落盘则是由后台线程异步完成的。

redo log 是如何保证持久性的？
如果在数据库刚把 redo log 刷盘，但数据页还没来得及刷盘时发生宕机，那么在重启时，InnoDB 存储引擎就会读取 redo log 文件，将那些已经提交但尚未刷盘的数据重新执行一遍刷盘操作，从而保证了数据的持久性。

此外，为了应对在 redo log 刷盘过程中可能出现的问题，MySQL 还引入了另一种机制——双写缓冲（Doublewrite Buffer），以确保能够顺利且安全地将数据写入。


#### 4.4.3 隔离性

主要是通过多版本并发控制（MVCC）以及锁机制来实现。


我们上面提到，它总共是有四个事务隔离级别。针对这四种隔离级别，实际上都是通过 MVCC 和锁机制，以不同的方式去进行实现的。


##### 4.4.3.1 锁机制

MySQL 的锁主要分为以下几类：

1. 记录锁 (Record Lock)
   它会锁住当前行的索引。首先，MySQL 的锁（特别是 InnoDB）基本都是行锁，但它依赖于索引，锁是加在索引上的，而不是直接加在数据行上的。如果你执行更新语句时，Where 条件里没有索引，它就会退化成表锁。

2. 间隙锁 (Gap Lock)
   它是锁住索引记录之间的间隙，主要是为了防止其他事务在这个间隙中插入数据，从而解决幻读问题。

3. 临键锁 (Next-Key Lock)
   它是记录锁和间隙锁的结合，既锁住这条记录本身，也锁住该记录之前的间隙（通常是左开右闭的区间）。

InnoDB 的行锁算法主要就是以上这三种：记录锁锁住索引的一条记录，间隙锁锁住记录间的空隙，而临键锁则是两者的结合。



##### 4.4.3.2 mvcc机制

MVCC 机制是 InnoDB 实现事务隔离的一种核心机制。它的核心思想是通过保存数据的多个版本，让读操作可以访问某个特定的版本，而写操作同时创建新的版本，从而实现读写操作的并发。

也就是说，读操作不需要等待写操作完成，而是直接读取一个快照版本；写操作也不需要等待读操作完成，而是在新版本上进行，这极大提高了并发性能。

MVCC 的实现主要由三个组件构成：

1. 隐藏字段
   在 InnoDB 的每一行中，都有三个隐藏字段：
   (a) 事务 ID（DB_TRX_ID）：记录最后一次修改该行的事务 ID
   (b) 回滚指针（DB_ROLL_PTR）：指向该行对应的 undo log 记录
   (c) 隐藏主键（DB_ROW_ID）：如果表没有主键，InnoDB 会自动生成

2. undo log 版本链
   undo log 是 InnoDB 负责回滚的日志，同时也构成了 MVCC 的版本链。每当对一行数据进行更新时，旧版本的数据不会立即删除，而是写入 undo log 中。新版本的“回滚指针”会指向 undo log 中旧版本的位置，而旧版本也有同样的回滚指针，指向更老的版本，从而形成一条从新到旧的版本链。

3. Read View（读视图）
   Read View 是决定哪个事务能看到什么数据的核心机制。可以将其理解为事务进行快照读时拍摄的快照。通过 Read View，可以保证事务只能看到自己有权访问的数据，从而实现对应的隔离机制。


Read View 的判断机制主要包含以下规则：

1. 事务自身修改：如果当前版本是该事务自己修改的，则对该事务可见。
2. 已提交版本：如果当前版本在 Read View 创建前就已经提交，则该版本对当前事务可见。
3. 后发版本：如果该版本是在 Read View 创建后才出现的，则对当前事务不可见。
4. 未提交修改：如果该版本是由尚未提交的事务修改的，同样不可见。

通过版本链配合 Read View 这种机制，实际上对事务能够看到什么数据进行了精确控制。



然后，MVCC 只对快照读生效。







### 4.5 InnoDB 的事务隔离级别实现

首先，InnoDB 将 SQL 的操作分成了两类：

1.  **快照读 (Snapshot Read)**
    它就是普通的 `SELECT`，不加锁，其底层完全依赖于 MVCC 机制。

2.  **当前读 (Current Read)**
    它主要是 `UPDATE`、`DELETE`、`INSERT` 等操作。它读取的是数据库中最新的数据，完全依赖锁机制。

接下来，我们详细讲解这四个隔离级别：

#### 4.5.1 读未提交 (Read Uncommitted)

这是最简单的隔离级别。

*   **快照读**
    它甚至不使用 MVCC，直接去读取最新的数据。如果其他事务修改的数据还未提交，它就会读取到这些未提交的脏数据。

*   **当前读**
    它会加上排他锁，阻止其他事务同时修改同一行数据。

#### 4.5.2 读已提交 (Read Committed)

读已提交级别解决了脏读问题。

*   **核心实现**
    其核心在于 MVCC 的生成时机：在每一次快照读之后，都会去生成一个新的 Read View。

*   **防止脏读机制**
    假如事务 B 修改了数据但尚未提交。此时事务 A 执行快照读时，会生成新的 Read View。由于事务 B 的 ID 活跃在事务列表里，根据 MVCC 的可见性，事务 A 是看不到事务 B 修改版本的，这样就防止了脏读。

*   **不可重复读问题**
    为什么它仍然是不可重复读呢？
    假设事务 A 第一次 `SELECT` (快照读) 生成了 Read View 1。随后事务 B 提交了修改。当事务 A 第二次 `SELECT` (快照读) 时，会生成新的 Read View 2。此时事务 B 已经提交，根据 Read View 2 的活跃列表，事务 A 就能看到事务 B 的提交。因此，两次读取到的数据就是不同的，导致了不可重复读。

*   **当前读**
    它的当前读只加记录锁，不加间隙锁。它只锁定具体匹配到的那一行，其他行仍然可以向旁边添加数据。这样的话，它也不能防止幻读。

#### 4.5.3 可重复读 (Repeatable Read)

可重复读解决了不可重复读的问题，并在很大程度上解决了幻读，但不是全部解决。

*   **快照读实现机制**
    事务只在启动时生成一次 Read View，后续就一直复用。

*   **解决不可重复读**
    事务 A 在第一次快照读时生成的 Read View 记录了此时活跃事务的列表。无论后续事务 B 如何提交修改，由于事务 A 一直都是拿着之前的 Read View 去判断的，导致事务 B 的版本对于它来说一直是不可见的。所以无论事务 A 读多少次，它读到的结果都是它原来读到的结果，这样就防止了不可重复读。

*   **防止部分幻读**
    假设事务 A 执行了一次快照读，读取了多行数据并生成了一个 Read View。此时事务 B 在事务 A 读取的那些数据里面插入了一条数据并提交了。当事务 A 再次执行时，因为它复用的是之前的 Read View，事务 B 新增的这条数据对于事务 A 来说就是不可见的，所以幻读就被防住了。

*   **当前读实现机制**
    当前读会加临键锁 (Next-Key Lock)。临键锁是记录锁和间隙锁的组合。
    *   **记录锁**：锁定已有的索引行。
    *   **间隙锁**：锁定两行之间的间隙，即一个左开右闭的区间。
    在可重复读级别下，InnoDB 会加上间隙锁，锁住事务 A 读取的区间。当事务 B 试图往里面插入数据时，就会被直接阻塞，直到事务 A 提交，强行防止了当前读的幻读。

*   **幻读的极端场景**
    虽然可重复读可以解决一部分幻读，但不能解决所有幻读。在一个极端场景下，它仍然会产生幻读：
    假设事务 A 执行快照读但没有找到数据，也没有生成 Read View。此时事务 B 插入了一条数据并提交。事务 A 再次执行当前读，由于加了锁，它会成功更新这条数据。当事务 A 再次执行快照读时，它可以看到事务 B 插入的数据，因为事务 A 自己更新了这条数据，这行数据的事务 ID 变成了事务 A 的 ID。根据 MVCC 规则，事务 A 可以看见自己修改的数据，所以它依然可以产生幻读。

#### 4.5.4 串行化 (Serializable)

串行化的快照读直接退化成当前读。

比如说你在串行化的级别下，执行普通的快照读，底层也会帮你转化成当前读。它会给你读取到的所有行和间隙都加上临键锁，这样的话所有的读和写都会相互阻塞，就相当于是单线程去执行的。

### 5.2 乐观锁与悲观锁

1. 悲观锁 (Pessimistic Locking)
   核心思想：默认并发冲突一定会发生，因此每次在操作数据前都会先加锁，保证同一时间只有一个事务能够修改数据。
   (a) 实现方式：主要通过 InnoDB 的行锁来实现。在查询数据时就进行加锁，直到事务提交后才释放锁。
   (b) 适用场景：适用于“写多读少”的场景。

2. 乐观锁 (Optimistic Locking)
   核心思想：默认冲突一定不会发生，因此在操作数据时不会加锁，只有在提交数据时才会校验数据是否发生了并发冲突。如果发生冲突，则回滚并重试。
   (a) 实现方式：主要通过版本号机制实现。在表中新增一个 version 字段，每次更新数据时将版本号加一。更新时校验当前版本号是否匹配，若不匹配（说明数据已被其他事务修改），则回滚重试。
   (b) 适用场景：适用于“读多写少”的场景。

## 7 日志

### 7.1 日志分类,两阶段提交


MySQL 的日志主要分为三类：Redo Log、Undo Log 和 Binlog。

1. Redo Log（重做日志）
   (a) 性质：属于物理日志，记录的是在某个数据页上做了哪些物理修改。
   (b) 作用：主要负责崩溃恢复（Crash-safe），保证数据库的持久性。如果数据库突然宕机，可以通过 Redo Log 直接恢复。
   (c) 原理：采用 Write-Ahead Logging（WAL）技术，在修改数据页之前，先将修改操作记录到 Redo Log 中，再由后台线程异步将数据刷入磁盘。
   (d) 恢复机制：重启时将 Redo Log 重新执行一遍即可。

2. Undo Log（回滚日志）
   (a) 性质：属于逻辑日志，记录的是反向的操作。
   (b) 作用：保证数据库的原子性，并配合 MVCC（多版本并发控制）机制形成版本链。
   (c) 工作机制：当执行一条更新操作时，它不会立即破坏旧数据，而是把旧数据拷贝一份到 Undo Log 里。
   (d) 回滚处理：如果事务执行失败需要回滚，就通过 Undo Log 把数据恢复到之前的状态。

3. Binlog（归档日志）
   (a) 性质：属于逻辑日志，记录的是所有对数据库进行修改的 SQL 语句。
   (b) 作用：主要负责数据备份和主从复制。
   (c) 特点：采用追加写的方式，文件可以无限大。因此，通常需要定期清理过期的日志。

4. 两阶段提交（2PC）机制
   在修改数据时，需要同时写入 Redo Log 和 Binlog。为了防止两个日志写入不一致导致的数据错乱，MySQL 引入了两阶段提交：
   (a) 准备阶段（Prepare）：将 Redo Log 写入磁盘，并标记为 prepare 状态。
   (b) 提交阶段（Commit）：将 Binlog 写入磁盘，再将 Redo Log 标记为 commit 状态。
   (c) 异常处理：
      - 如果宕机发生在准备阶段之后、Binlog 写入之前：重启后发现 Redo Log 处于 prepare 状态但没有对应的 Binlog 记录，则直接回滚该事务。
      - 这样可以确保 Redo Log 和 Binlog 的数据保持统一。

除了这三大日志之外，MySQL 还有一些其他的日志，比如慢查询日志（Slow Query Log）和错误日志（Error Log）等。


什么是 WAL 机制？

简单来说，它在修改数据时不直接同步修改磁盘，而是先将修改记录写入到 Redo Log 里，同时修改内存中的数据并提交事务。后续由后台线程在数据库空闲时，将缓冲池中的数据刷回到磁盘里，完成持久化。




## 8 SQL 与大表性能优化

### 8.1 如何定位和优化一条慢 SQL？完整的排查优化流程是什么？


如何定位和优化一条慢 SQL？

1. 开启慢查询日志
   首先，第一步是打开慢 SQL 查询日志（Slow Query Log）。一般来讲，执行时间超过一秒的 SQL 语句都会被记录到该日志中。

2. 使用 EXPLAIN 分析执行计划
   从日志中获取到具体的 SQL 语句后，使用 EXPLAIN 语句对其执行计划进行分析。一般主要观察以下核心指标：
   (a) Type（访问类型）：查看是否出现了全表扫描，性能是否达到了 range 及以上的级别。
   (b) Key：查看是否命中了索引。
   (c) `rows`：扫描的行数是否过多，和返回行数差距是否过大。
   (d ) `Extra`：是否出现 Using filesort（文件排序）、Using temporary（临时表）、Using were（回表）等需要优化的场景。

4. 核心问题归类与优化
   通常慢 SQL 的核心问题主要分为三类：
   (a) 索引问题：没有建立索引、索引失效或者索引设计不合理。
   (b) SQL 语句问题：SQL 编写不规范。例如使用了 SELECT *、联表查询（Join）过多，或者深分页问题，都会导致性能下降。
   (c) 表结构问题：表中字段类型定义不合理、大字段过多或单表数据量过大。












## 9 主从复制

### 9.1 MySQL 主从复制的核心原理是什么？完整流程是怎样的？
MySQL 的主从复制主要是基于 Binlog 来实现的。其核心流程是主库将所有的更新操作写入 Binlog，从库通过同步并执行这些 Binlog 内容，从而实现主从库的数据一致性。

具体流程如下：

1. 主库将所有的更新操作（如增删改）记录到 Binlog（归档日志）中。
2. 从库的 I/O 线程连接到主库，拉取 Binlog 内容，并将其异步写入到从库本地的 Relay Log（中继日志）中。
3. 从库的 SQL 线程读取 Relay Log 的日志内容，将其解析为 SQL 语句并按顺序执行，从而完成数据的重放，实现主从数据的一致。

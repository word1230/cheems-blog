## spring
2. Springboot 自动装配原理


Spring Boot 的自动装配原理主要分为两个部分：

1. 资源加载
   (a) 将预先设置好的配置类加载进来。在 Spring Boot 主类上有一个核心注解 `@SpringBootApplication`（这是一个复合注解），其中与自动导入相关的是 `@EnableAutoConfiguration`。
   (b) 在 Spring Boot 2.7 之前，加载逻辑是扫描项目依赖中 `META-INF/spring.factories` 文件，该文件以键值对（Key-Value）的形式配置了自动装配类。
   (c) 从 Spring Boot 2.7 开始，加载逻辑改为扫描 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件。该文件包含了所有需要被自动加载的全限定类名列表。

2. 条件筛选与排除
   (a) 根据 `@EnableAutoConfiguration` 的 `exclude` 属性或 `spring.autoconfigure.exclude` 配置，排除掉不需要的配置类。
   (b) 通过 `@Conditional` 系列注解（如 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 等）进行条件过滤。并非所有加载进来的配置类都会生效，系统会筛选满足特定条件的类（例如某个 Bean 或类是否存在）。
   (c) 最终实现按需配置，用户还可以通过 `application.yaml` 或 `application.properties` 文件对这些自动装配类的属性进行自定义修改。



3. 如何实现自己的类自动装配
主要有以下两种方法：

内部项目快速加载
   如果你只是想在自己的项目里使用，可以直接在类上添加 @Component 等注解，这样该类就会被自动扫描并加载到 Spring 容器中。

自定义 Starter 实现自动装配
   如果你希望实现的是一个通用的类，能够被其他人调用，或者在其他不同的项目中使用，那么建议通过自定义 Starter 的方式来实现。具体步骤如下：

   (a) 编写业务类与配置类
       首先编写好你的业务逻辑类。接着创建一个配置类，使用 @Configuration 注解进行标注。

   (b) 设置条件注解与属性绑定
       在配置类中，你可以结合 @Conditional 系列注解（如 @ConditionalOnClass、@ConditionalOnProperty 等）来控制装配条件。同时，如果你想让某些字段支持外部化配置，可以配合 @ConfigurationProperties 来绑定 application.properties 或 application.yml 中的参数。

   (c) 创建发现文件（关键步骤）
       这是最关键的一步。你需要在项目的 resources 路径下新建配置文件：
       - Spring Boot 2.7 以前：在 META-INF/spring.factories 中写入配置类的全路径。
       - Spring Boot 3.0 及以后：在 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 文件中写入你的配置类。

   (d) 自动装配生效
       完成上述配置后，当其他项目引入你的这个模块并在启动时，Spring Boot 会自动加载并装配你定义的类。

为了更好地管理代码，你还可以将 Starter 进一步拆分：创建一个真正的启动器（Starter）模块只负责依赖导入和外壳定义，而将真实的自动配置逻辑放在另一个 Autoconfigure 模块中。这样，其他人只需要导入你的 Starter 依赖即可直接使用。






4. aop原理 方式
原理是通过动态代理以及拦截器链的方式实现的。

具体来说，AOP 在运行时会为一个被增强的 Bean 创建一个代理对象。客户端实际上是调用这个代理对象，而代理对象的内部维护了一个拦截器链。

这个拦截器链上的每个节点都对应一个通知（Advice）。通过代理对象，就可以实现 AOP 的功能：
	1. 以环绕通知（Around Advice）为例，它通过拦截器链中的递归调用来实现。
	2. 每个环绕通知的拦截器都持有对下一个拦截器的引用。
	3. 它通过显式调用 `proceed` 方法来决定是否将控制权传递下去。

5. 如何自定义线程池的拒绝策略


主要的拒绝策略相当于有四种：

	1. 抛出异常。
	2. 直接丢弃。
	3. 交给调用者（上一个线程）处理。
	4. 去掉最老的消息（小节），然后将新消息存入。

如果要实现自定义策略，需要实现 RejectedExecutionHandler 接口，并重写其中的 rejectedExecution 方法。

在这个方法里，你可以根据业务需求规定任务被拒绝后的最终行为。例如：
1. 记录日志：当任务被拒绝时，打印一份 warning 日志。
2. 监控告警：通过度量指标（Metrics）报告当前线程池的状态，比如活跃线程数、队列长度、当前任务类型等。
3. 外部通知：上报监控平台、发送邮件或给特殊组件发送告警。
4. 降级处理：进行一些业务上的兜底或降级逻辑。
5. 最终决策：决定是抛出异常，还是静默丢弃，这完全取决于具体的业务选择。

9. 为啥图数据库不存在mysql里

因为实际上 MySQL 更加适合存储的是一些类似 Excel 的表结构，它利用的是表之间的关联关系。而对于图数据库（Graph Database）来讲，它更加擅长处理的是实体与实体之间的联系。

比如我们存储的天、周、节点、状态等，它们之间是相互关联的。在分配任务或进行计算时，都需要频繁使用这些关联关系。如果把这些数据放到 MySQL 中，虽然确实可以用，但在处理复杂关系时显然不够精确，而且操作起来非常繁琐。

特别是在数据量较大的情况下，比如用户原有的计划崩溃了，我们需要为他重新生成一份计划。我们不能直接丢弃旧计划，当时的处理方式是将旧计划中未完成的任务裁掉，然后生成一份新计划接在之前的计划后面，同时过滤掉已经完成的任务。如果使用 MySQL 去查询和衔接这种计划，逻辑会非常复杂。

所以，使用图数据库来实现这种方案显然更加合适。一方面是因为之前已经做过相关的同步工作，另一方面也是考虑到这种场景下，图数据库在处理实体关联和计划路径时的优势。

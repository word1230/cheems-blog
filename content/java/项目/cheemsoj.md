## 判题流程

用户提交题目

1. 校验： 校验是否符合规定的语言，题目是否存在
2. 设定题目状态为等待，判题信息为空，提交题目
3. 执行判题服务
	1. 校验参数： 判断题目是否存在，提交信息是否存在，题目状态是否为等待
	2. 更新题目状态为判题中
	3. 获取输入用例，调用沙箱获取执行结果
	4. 根据沙箱执行结果和设定的case进行对错判断逻辑（策略模式）
		1. 对于c c++ python这种
			1. 先判断沙箱输出数量与预期数量是否相等
			2. 判断每一项输出于预期结果是否相等
			3. 判断题目内存 和时间限制
		2. 如果是java这类
			1. jvm启动安照10s计算
	5. 判断完成后返回判断结果
	6. 修改数据库的判题结果和判题信息
	7. 将判题结果返回

首先，用户将代码提交到后端后，后端会进行参数校验，比如校验编程语言是否是规定的类型，然后检查用户提交的题目是否存在，接着构建一个提交记录并存储到数据库中，设置这个提交记录的初始状态。

接下来是执行判题，这里先构建一个消息存储到消息发件箱表中。然后每五秒会有一个定时任务，从消息表中捞出最近尝试时间小于当前时间、最大重试次数小于最大重试次数，以及状态为待提交的消息，大概二十条，通过消费者发送出去，同时更新发件箱中消息的状态。

在消费者端，会调用判题服务，判题服务会调用代码沙箱。在代码沙箱中，先存储用户的代码并生成临时文件，然后进行编译，打开一个Docker容器，将代码复制进去执行，获取执行结果，然后删除临时文件。

拿到执行结果后，进行判断正误的服务，这里会从题目信息表中获取每道题的用例，将Docker容器输出的结果与用例进行比对，比如数量和每个用例的结果是否正确。判断完成后，再检查内存和时间消耗是否符合题目的要求，这样得到判题结果。

最后将判题结果更新到提交记录中，同时更新提交记录的状态，用户就可以在前端提交记录那里看到自己的提交记录。








## 你为什么选 Spring Boot + Docker + Redis + RabbitMQ 这一套？每个组件分别解决什么问题？

首先，Spring Boot是Java web开发的必备框架，

Docker是开发OJ系统所需的必要组件，当然你也可以使用原生方式在服务器本机安装Java环境来编译执行代码，但这样会有安全问题，比如用户在代码中写死循环或恶意代码，会占用服务器主线程或耗尽资源，虽然可以在代码中做限制，但终归不安全。所以使用Docker，容器与主机隔离，用户在容器中的行为不会影响主机，如果用户做了危险代码，只需销毁容器即可解决。

Redis主要是我在做项目过程中发现，数据库题目信息表存储的是JSON格式，导致主页获取题目列表较慢。基于这个问题，我目前使用Redis做缓存提高访问速度，之后考虑将用例移动到文件中，存储到对象存储中，通过动态读入来提高访问速度。

RabbitMQ用于判题的异步操作，用户提交代码后不用一直等待结果，可以继续做下一道题或查看当前题目的结果。

## 你说“自主设计判题机模块架构”，那你先讲一下判题模块的核心分层。




这个判题机架构主要分为两个部分，第一个是执行代码，也就是代码沙箱这一部分，第二个是判断代码执行结果与预设用例结果是否相同，也就是判断正确性的部分。

第一部分主要采用代码沙箱的形式，你可以采用原生的Java代码沙箱，也可以调用自己编写的代码上传，或者调用第三方写好的代码上传。为了先跑通流程，我写了一个示例代码上传。这里定义了一个代码上传工厂，工厂由配置决定具体调用第三方代码沙箱、远程代码沙箱还是本地代码沙箱，配置文件中进行配置。通过工厂模式，根据不同参数生成不同的代码生成实例。然后通过简单的动态代理给代码沙箱执行监控，增加执行日志。这个项目主要使用远程代码沙箱，也就是我自己编写的。

然后对于远程代码沙箱的话，这里主要有两种实现，第一种就是Java原生的实现，这种方式是在本地调用本地终端，然后传递参数去执行和编译Java文件，直接拿到对应的结果，当然这种方式有很大的缺陷和安全隐患，所以还增加了使用Docker容器进行的方式。同时，因为这两种方式只有运行代码的方式不一样，其他整个流程包括生成临时代码、编译代码、运行、获取结果、删除临时代码，这一整套流程是一样的，因此这里就采用了一个模板方法模式来减少重复的代码


第二部分是执行判题结果。对于C语言和Java语言的执行对比，Java语言因为要启动虚拟机等原因，执行速度更慢，因此在内存和执行时间的判断上需要有所不同。这里采用策略模式进行区分，在执行判题前先获取当前题目的语言，如果是Java就走Java的判题策略，如果是C语言就做C语言的判定策略，然后在判定策略里做对应的处理。





判题机的话，首先第一个是用户在提交代码到后端之后呢，对这个参数进行校验，然后同时呢，将生成一个提交记录，记录进行落库。

嗯，在这个部分呢会校验这个用户比如说用户的这个提交的题目是否存在语言是否符合预设，然后去生成一条提交记录并且设置这个提交记录的状态，然后去生成一条消息，然后存储到发件箱中。

第二部分的话是去发起这个调用运行代码运行层调用第三部分，他呢主要是负责获取到这个提交记录题目信息测试用例，然后将这些信息呢传给这个代码沙箱。

代码沙箱进行这个判题，第三部分呢就是这个代码沙箱部分，在这个部分呢主要负责将用户的代码呢转成这个应试文件，然后转成临时文件，然后进行编译运行，然后获取到运行结果，然后处理掉这个临时文件和生成的docker容器，这是代码平层。

### 第一部分：你的自适应学习计划是如何实现的？请总体描述一下


首先，整体计划分为四个阶段。核心思路是建立一套学习路径，并根据不同的阶段采取相应的策略为用户分配题目。

具体实现分为以下几个模块：

1. 学习路径与知识点构建
   基于图数据库建立一个“考点图谱”，将所有知识点组织成类似“树”的结构。
   (a) 提取路径节点：从学习路径中抽取知识点（节点），按照一定规则进行排列。
   (b) 关联资源：每个知识点下都关联了相应的题目和讲解视频。

2. 阶段化题目分配
   整个计划包含四个阶段：理论学习、题目模块、实战和冲刺。
   (a) 系统会根据用户所处的阶段，应用不同的规则和策略来分配题目。
   (b) 系统会预先给出用户一周的学习计划，明确每天需要掌握的内容。

3. 动态调整机制
   学习计划是动态变化的。如果用户某天学的比较多，或者当天没有学习，系统会根据用户的实时动作进行动态调整。

4. 评估机制与指标
   通过多个维度的指标对用户的学习进度进行判断：
   (a) 周目标：例如完成周内所有任务，或至少完成 80%。
   (b) 阶段任务：设定预测分达标要求。
   (c) 量化指标：包括总学习时长、做题量以及任务完成比例。
   (d) 进度状态：判断计划是“崩溃”、“提前”还是达到了“最小要求”。

我主要负责的部分包括：考点路径的计算、阶段目标的计算，以及学习进度评估中的状态计算。



其中，考点路径的计算主要是基于我们之前的考点图谱。我们利用图数据库形成了一个类似于树形的考点图谱，将所有的知识点都包含在内，构建出一个层级结构。

考点路径的具体形成过程如下：

1. 获取根节点：
   从根节点开始向下递归，获取所有的子节点。

2. 排序与价值计算：
   在递归过程中，需要对节点进行排序。排序是根据“考点价值”来衡量的。
   考点价值是根据产品的预设公式，综合考点的分数、难度以及考评情况计算出来的。

3. 资源关联过滤：
   为了保证路径的有效性，如果某个节点没有关联任何学习资源，系统就不会将其记录到考点链中，而是直接将其剔除。

4. 链表构建：
   通过上述步骤，从底层向上层节点逐级连接，最终构建出一个完整的链表结构。

5. 用户偏好过滤：
   在链表构建完成后，还需要根据用户的偏好进行过滤。
   (a) 用户偏好（如希望先学什么、不想学什么）以数据表或数字图链的形式存储在数据库中。
   (b) 系统读取这些偏好数据，从已有的考点链中过滤掉不符合要求的内容。

最后，系统保留用户需要的考点路径并进行返回。这就是考点路径计算的核心逻辑。


### 学习计划的评估逻辑

关于学习计划的评估，其核心在于计算目标是否达成。目标主要分为总目标和阶段目标：

1. **目标达成标准**
   主要考察以下几个维度：
   (a) 是否达到预测分的标准
   (b) 学习时长是否足够
   (c) 完成的题目数量是否达标

   总目标和各个阶段目标都有各自预设的目标量。

2. **状态评估逻辑**
   评估是分阶段进行的，主要分为“周评估”和“阶段评估”，系统会根据计算结果给出相应的状态：

   * **周评估（已完成/进行中/无法完成）：**
     (a) **已完成：** 如果今天在周内且所有任务已完成，或者已经过了本周截止日且所有任务均已完成，状态为“已完成”。
     (b) **进行中：** 任务按计划推进，完全没有问题。
     (c) **无法完成：** 如果今天虽然在周内，但按照每周最大学习时长计算，已经无法完成剩余任务，则状态判定为“崩溃”（即无法完成）。

   * **阶段评估：**
     (a) 如果用户处在阶段中，但阶段考点路径里的所有考点都已学完，视为提前完成。
     (b) 如果在当前阶段内，模拟任务按照最大学习时长也无法完成，状态同样判定为“崩溃”。

3. **数据计算与技术实现**
   这里涉及两种计算法（周计算和阶段计算），采用的是从底层向上汇总数据的思路：

   * **数据维度：** 按照“天 → 周 → 阶段 → 整体”的维度层层递进。系统会从每天的节点中，将学习时长等属性累加起来，再按照预设规则进行判断。
   * **事件机制：** 采用基于事件的机制。当用户进入系统时，首先进行周判断。
   * **调用逻辑：** 周判断完成后，会同时进行周计算和阶段计算。系统会优先判断阶段状态，如果阶段已经处于“崩溃”状态，则直接调用相应逻辑；如果阶段没有崩溃，则继续正常的调用流程。



## 关于sub-agent

这里的 Memory tool 其实就是 Claude 官方指出的方向。他指出通过给 Claude 模型提供工具，让模型能够自主决定去调用这些工具。

具体实现上，你需要写好一个类似于文件系统的资源操作接口提供给它即可。我这部分主要做的是：

1. 使用阿里的对象存储 OSS
   (a) 构建了一套通过文件基本操作（以及修改文件）来实现的逻辑
   (b) 这包含了一套递进式的方案，以及一套通用的、在 OSS 中使用的模式



2. 学习计划评估逻辑与 Sub-Agent 内存工具

这个 Sub-Agent 的运作逻辑如下：

1. 主进程（Main Agent）职责：
   负责与用户进行交互，涵盖学习计划的相关咨询，包括计划调整、进度跟踪（如学习到哪一阶段了）以及提供相应的反馈等。

2. 子 Agent（Sub-Agent）职责：
   (a) 接入了专门的学科答疑模型，专门负责为用户提供学科内容的解答。
   (b) 该学科答疑模型被封装成了一个工具。

3. 调用流程：
   (a) 主进程负责判断用户的需求，如果识别到是学科答疑方面的问题，则会通过工具调用（Tool Calling）来启动子 Agent。
   (b) 调用完成后，系统将结果返回给主进程，由主进程统一向用户进行回答。



同时，系统还会触发学习状态的变更。例如，当学习状态重新启动或更新时，会向用户发送一个卡片，用户可以通过该卡片对之前的自适应学习计划进行调整。

这也是通过工具调用（Tool Calling）实现的，具体逻辑如下：

1. 处理用户个性化要求：
   当用户提出“不想学习当前内容”或“希望提前学习某项内容”时，系统会调用对应的修改工具。

2. 执行修改动作：
   (a) 修改考点路径。
   (b) 修改今日的学习内容。
   (c) 调用重新生成技术，更新学习计划。

## 关于 评测

这部分，主要是当时产品要求我们去测试另一个团队的“预测分身”模型是否可用。

为了测试这个结果的返回值是否符合预期，我们按照不同的场景进行了测试。

测试主要涵盖了单轮次和多轮次场景下，用户答题正确率起伏对“预测分”变化的影响。

以数学计算评测为例，测试流程如下：
1. 构造参数并请求接口：
   我们先去构造对应的参数并请求接口。
2. 汇总数据：
   请求接口后，将返回的 JSON 数据进行汇总。
3. 填充表格：
   由于测试用例（Case）非常多，最终我们会将汇总后的结果直接填入 Excel 表格中。

在具体的实现层面：
1. 自动化规划：
   考虑到测试场景的多样性，我直接调用了 AI 来做一个自动化的规划。
2. 函数调用与参数解析：
   通过编写一个内部函数，解析其中的不同参数。这些参数包括：
   (a) 题目信息：具体的题目编号。
   (b) 科目信息：该题目所属的科目。
   (c) 难度等级：题目的难易程度。
   (d) 答题状态：用户回答正确或错误的情况。
3. 模式匹配：
   根据解析出的不同参数，程序会切换到不同的模式（如 Tool, Agent, OSS, Claude 等）来获取预测结果，并最终将其填入 Excel。

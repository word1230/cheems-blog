## 判题流程

用户提交题目

1. 校验： 校验是否符合规定的语言，题目是否存在
2. 设定题目状态为等待，判题信息为空，提交题目
3. 执行判题服务
	1. 校验参数： 判断题目是否存在，提交信息是否存在，题目状态是否为等待
	2. 更新题目状态为判题中
	3. 获取输入用例，调用沙箱获取执行结果
	4. 根据沙箱执行结果和设定的case进行对错判断逻辑（策略模式）
		1. 对于c c++ python这种
			1. 先判断沙箱输出数量与预期数量是否相等
			2. 判断每一项输出于预期结果是否相等
			3. 判断题目内存 和时间限制
		2. 如果是java这类
			1. jvm启动安照10s计算
	5. 判断完成后返回判断结果
	6. 修改数据库的判题结果和判题信息
	7. 将判题结果返回

### 策略模式 / 判题算法

### - 你为什么觉得这里必须用策略模式，直接 if-else 会带来什么具体问题？


关于为什么要使用策略模式，而不是直接使用 if-else，主要有以下几点考虑：

1. 业务代码的耦合与维护
   如果直接将判断逻辑编码在业务代码中，会导致代码中出现大量的 if-else 分支。后续如果需要增加新的策略，就必须修改原有的业务代码，这违背了开闭原则。

2. 性能差异的处理
   使用策略模式也是为了应对 Java 层在编译和运行效率上的特性。相比于 C 语言，Java 的运行速度通常较慢，因为 Java 需要先编译成字节码，然后再由 JVM 运行。

3. 运行环境的额外处理
   由于上述的性能差异，我们需要针对不同的策略进行额外处理。例如：
   (a) 为特定的策略增加更多的执行时间
   (b) 为其分配更多的内存空间

通过策略模式，我们可以更灵活地实现这些差异化配置。

## RabbitMQ + Transactional Outbox

  - 你为什么不用“提交后直接发 MQ”，而是要引入 Outbox？

一个发件箱的目的是为了保证消息不会丢失，如果你不使用发件箱，直接调用生产者发送消息，比如生产者刚将消息发出，此时消息队列服务终止了，那么消息就会在这个过程中丢失，但是因为你已经修改了提交记录的状态，导致提交记录永远卡在这个状态，无法继续流转。

你使用了AutoBox的话，它首先引入AutoBox是因为它实际上是一个数据库，通过这个数据库的事务来实现同步的更改，因为你在更改状态后，需要同时把消息存储到发件箱中，以此保证状态修改与消息的状态是一致的，避免因消息队列无法正常使用而导致状态无法流转下去的问题。




为什么不直接在提交后发送 MQ，而是引入 Outbox（发件箱）模式？

首先，整体流程如下：
1. 参数校验：用户从前端将代码提交到后端，后端先进行参数校验，包括题目 ID、语言是否为预设语言等。
2. 提交记录：校验通过后，向 MySQL 提交一条记录，包括初始化判题状态（等待判题）和初始化判题信息。
3. 生成消息：在同一个事务中生成一条消息，存入数据库的 Outbox 表（发件箱）中。
4. 消息处理：
   (a) 由采集线程（或定时任务）从数据库中读取消息并发送到消息队列（MQ）。
   (b) 消费者基于线程池调用后端的判题服务。
5. 执行判题：
   (a) 判题服务将提交记录中的状态改为“判题中”。
   (b) 调用代码沙箱获取执行结果。
   (c) 由判题服务依次对比执行结果与预设用例是否一一对应，从而给出最终判断结果并返回。

那么，为什么要使用 Outbox 模式呢？

如果直接在提交后发送 MQ，可能会遇到以下问题：
1. 消息丢失：如果你在发送 MQ 时，消息队列正好中断或崩溃了，导致消息发送失败。
2. 状态不一致：由于发送失败，你可能认为发送成功了（或者本地事务已提交），但实际上消费者并没有收到消息。这会导致提交记录的状态一直卡在“判题中”或“等待判题”，无法继续向下流转。

引入 Outbox 模式的核心目的就是为了保证消息不丢失。通过将消息和提交记录放在同一个数据库事务中进行提交，可以确保两者的原子性，从而彻底解决状态流转中断的问题。








如果你直接发送 MQ 而不用发送箱（Outbox）的话，就会导致以下两种情况：
1. 提交记录入库成功，但消息发送失败；
2. 消息发送成功，但提交记录入库失败。

这会导致消息提交的状态永远卡在“等待中”，无法继续向下流转，导致状态不完整。

这里引入 Outbox 模式，主要是为了保证“双写”的一致性，确保操作可以成功，同时保证消息不会丢失。






  - question_submit 和 mq_outbox 是怎么保证在一个事务里的？


这里的情况是：两个表都在同一个 MySQL 中，同时我在代码上加了 Spring 的事务注解，保证两个消息走的是同一个事务。这样要么同时成功，要么同时失败。






  - 如果数据库事务成功了，但 MQ 发送失败了，会发生什么？


当 MQ 发送失败后，系统会从数据库中读取并修改 Outbox 表（发件箱）中的数据状态：

1. 更新重试信息：
   (a) 将重试次数加 1
   (b) 将下一次重试时间设置为 30 秒后
2. 判断重试限制：
   系统会判断是否已达到最大重试次数。如果达到上限，则将该记录的重试时间改为空。

接下来，MQ 会由下一个定时任务（每 5 秒执行一次）进行补偿处理。该任务会再次从 Outbox 中读取符合以下条件的记录：
- 重试次数不超过最大重试次数
- 重试时间小于当前时间
- 按照 ID 顺序筛选（例如每次选出 20 条）
- 状态处于等待和失败

读取到这些记录后，系统会重新将其发送给消费者进行消费。

我这里采用的是定时任务的方式去扫描 Outbox 表，具体的处理逻辑如下：

1. 筛选逻辑
   从中筛选出状态为“等待”和“失败”的记录，且满足以下条件：
   (a) 重试时间小于当前时间
   (b) 重试次数小于最大重试次数
2. 数据排序与提取
   按照 ID 进行排序，每次筛选出 20 条记录。
3. 消息发送
   将筛选出的记录发送给消费者进行消费。

关于扫描频率，设置是每 5 秒钟进行一次。
失败的话会等待 30 秒后重试。

关于 5 秒的扫描频率，这是一个折中的方案。因为这属于一种判定服务（Judge Service），不需要极高的实时性，但也不能太慢。设置 5 秒是为了平衡数据库压力与业务需求。

如果后续业务量增长，我会考虑将目前的“扫表”方式，替换为通过 Binlog 驱动或者 CDC（Change Data Capture）模式。


  - 你这个方案保证的是 at-least-once、at-most-once 还是 exactly-once？

这套方案保证的是 at-least-once，也就是至少投递一次，不保证绝对不重复。  
我是刻意偏向“不丢消息”这一侧的，因为在分布式场景里，端到端 exactly-once 成本很高，通常工程上更现实的做法是 at-least-once + 幂等消费。



这里保证每个消息至少投递一次，但它会出现重复投递的情况。

因为我这里处理的是判题逻辑，判题是绝对不能丢消息的。虽然用户一直点击，加上前端也加了防抖，不会触发第二次提交。但如果这次提交失败了，给用户的体验会比较差，所以这里实现的是“至少一次”（At-least-once）投递。

这里会出现重复投递的情况。如果消息发布或投递失败，系统会尝试修改数据库中 Outbox 表的消息状态。但如果修改数据库这一步失败了，导致消息状态没能成功更新，系统就会继续尝试重发，甚至可能超过最大重试次数。另一种情况是，虽然投递成功了，但修改数据库状态时失败，同样会导致系统再次发送，从而产生重复消息。

针对这个问题，我在后续的判题逻辑中做了处理：

1. 状态校验
   在执行判题前，系统会先判断这条消息的状态。如果消息处于“判题中”或“已判题完成”，系统会直接跳过该消息。

2. 流程回馈
   跳过后，系统不再重复执行判题逻辑，而是直接进入给消费者回馈的流程。

通过这种方式，从业务层面上阻止了重复判题的可能性。









  - 如果消息重复投递了，你怎么保证判题不会重复执行？
当前项目的思路是靠业务状态机兜底。判题记录一开始是 WAITING，消费时先检查状态，不是 WAITING 就直接跳过；开始执行前把状态改成 RUNNING，完成后改成 SUCCEED 或 FAILED。这样大多数重复消息都会被挡住。  
但我也会诚实说，这个实现现在是“有幂等意识”，还不是最强版本。更稳妥的做法应该是把“WAITING -> RUNNING”改成带条件的 CAS 更新，比如 where id = ? and status = WAITING，这样并发重复消息也只能有一个线程抢到执行权。







  - 你用了手动 ACK，那 ACK 的时机是什么？如果判题中途异常，你怎么处理？


我这里是手动 ACK，只有在 judgeService.doJudge() 真正执行成功，并且判题结果已经落库以后，才 ACK。  
如果判题中途异常，我不会 ACK，而是 basicReject(requeue=false)，让消息进入死信队列。同时业务侧会把这次提交状态更新成 FAILED，并记录错误信息，避免消息失败了但业务状态一直卡在处理中。




  - 失败消息进死信队列之后，后续怎么消费、告警或人工处理？

当前项目已经把 DLQ 配好了，但还没有把 DLQ 的自动化运维链路补完整。现在更像是一个兜底沉淀区，方便人工排查。  
如果上生产，我会补三件事：第一，给 DLQ 单独做监控和告警；第二，提供一个人工回放工具，可以把修复后的消息重新投递；第三，把死信原因、重试次数、traceId 打通到日志和监控系统里，便于定位问题。


  - 你有没有做 publisher confirm？
当前这个版本还没有把 publisher confirm 和 return callback 接上，这一点我会直接说明。现在是 convertAndSend() 不抛异常，就把 outbox 标成 SENT，这在工程上是有风险的。

  - 为什么 convertAndSend() 成功返回就把 outbox 标成 SENT，这里会不会有一致性风险？



会，这里确实有一致性风险。因为 convertAndSend() 成功返回，只能说明客户端这次发送调用没有抛异常，不等于 Broker 一定已经持久化成功，也不等于消息一定路由到了目标队列。  
更稳妥的做法应该是：发送时带上 correlationData=outboxId，开启 publisher confirm。只有收到 Broker 的 confirm ack 后，才把 outbox 标成 SENT；如果收到 nack，或者消息不可路由被 return，就把 outbox 标成 FAILED 并记录原因，后面继续补偿。  
所以如果面试官问到这里，我会说：当前方案已经解决了“业务事务和消息落地”的大问题，但在“发布确认”这一层还可以继续增强，这也是我下一步会优化的点。



## 并发控制
### 你控制并发，是在 MQ 消费端控制，还是在 sandbox 执行端控制？

这里的并发控制主要分为三层：


1. 第一层是 RabbitMQ，主要负责积压消息
   它在收到消息后，不会立即交给消费者，而是将消息积压下来。我通过自定义 RabbitMQ 工厂，设定了最大消费线程数以及每条消息的预取值（prefetch count），通过这种方式限制任务的下发速度。

2. 第二层是在调用判题服务时，采用固定大小的线程池来限制并发
   我增加了一个全局的判题执行线程池。在调用判题服务时，会从线程池中选择线程触发任务。
   (a) 如果当前消息超过了核心线程数，会创建新线程直到达到最大线程数。
   (b) 如果达到最大线程数，任务会被放入有界队列。
   (c) 如果有界队列也满了，系统会触发拒绝策略，任务会保留在之前的 MQ 队列中。

3. 第三层是在实际调用 Docker 沙箱之前，增加信号量（Semaphore）进行控制
   在调用前，程序会直接执行 acquire 操作获取许可，并在最终的 finally 块中进行 release。如果没有拿到许可，任务就无法继续向下进行，只有拿到许可的请求才能真正进入代码沙箱进行调用。


我这套方案的优先级是：

先排队，再限流，最后必要时降级，不会直接放开执行。

具体行为是分层的：

- 第一层，提交请求会先正常落库，写入 question_submit 和 mq_outbox
- 第二层，Outbox 把消息投递到 RabbitMQ，RabbitMQ 负责削峰，先把压力吸收住
- 第三层，判题消费者不是无限执行，而是固定并发消费
- 第四层，进入判题线程池后，如果线程池还有空位就执行，没有空位就排队
- 第五层，真正调用 sandbox 前还要拿并发许可，没有许可就继续等待，不创建新容器

所以如果瞬时来了 1000 个提交，正常行为不是同时创建 1000 个 Docker 容器，而是：

- 大部分任务先堆在 MQ 里
- 少部分进入判题线程池等待
- 同一时刻真正执行的任务数被固定住

如果再继续打满，我会做两种处理：

- 短期方案：继续排队，前端给用户展示“等待判题中”
- 极端情况：进入降级，比如限制单用户提交频率、暂停低优先级任务、或者把线程池满的任务转入延迟重试

当前设计里，我的取舍是：

宁可让任务排队变慢，也不让宿主机因为容器暴涨直接崩掉。

扩容不是第一反应。  
扩容通常是后续能力建设，比如把 sandbox 独立部署、多节点水平扩容；但在单机 4核4G 条件下，核心目标是先稳住资源，不是让系统假装可以无限吞吐。


### 为什么并发控制能减少 Docker 容器过量创建？

为什么要控制能减少 Docker 容器过量创建？

原因如下：
如果是多个用户同时点击提交代码，就会有多个线程同时运行并进入执行判题逻辑。这种情况下，系统会去执行 Docker 判题，从而创建多个容器。如果没有并发控制，就会导致容器过量创建，进而占满服务器的资源。

因为在这个系统里，Docker 容器不是独立产生的，它是判题链路执行到 sandbox 阶段的结果。

原来如果不控并发，链路是：

收到消息 -> 直接 doJudge -> 直接调 sandbox -> sandbox 直接 createContainer

那消息来多少，短时间内就可能触发多少次容器创建。  
问题不是 Docker 自己暴涨，而是上游没有“闸门”。

加并发控制之后，链路变成：

收到消息 -> 先进入固定容量执行池 -> 再拿 sandbox 并发许可 -> 然后才允许创建容器

这意味着：

- 不是所有提交都能立即走到 createContainer
- 只有拿到执行工位的任务，才会继续往下走
- 只有拿到 sandbox permit 的任务，才会真正创建容器

所以容器数的上限，就不再由“提交量”决定，而是由“并发控制参数”决定。

换句话说，并发控制本质上是在做这件事：

把请求量和资源消耗解耦。

用户可以一下来 1000 个提交，但系统不会因此一下创建 1000 个容器。

### 并发数是怎么定的？拍脑袋，还是按 CPU / 内存 / 单任务资源占用估算？

关于并发数，这里说明一下：

因为我目前用的是四核 4G 的配置，在部署时已经把 RabbitMQ、Redis、前端、后端，还有 Sandbox（判题沙箱）全部跑在这一台机器上了。

因此，系统剩余的可用内存其实并不多，所以我对配置做了一些限制：
1. 消息队列的并发数只剩了 2 个
2. 线程池的大小也只有 2 个
3. 队列长度限制为 20
4. 线程池的并发处理数同样只有 2

这确实是因为资源比较紧张。在部署完成后，这些服务大概就已经占用了 80% 左右的内存。


不是拍脑袋，是按资源预算估的，而且要取保守值。

我一般按这三个维度一起看：

- CPU 核数
- 可用内存
- 单任务真实资源消耗

可以用一个简单思路：

最大并发 = min(CPU允许并发, 内存允许并发, 系统安全上限)

比如你这个场景是 4核4G，而且还不是纯判题机，机器上还跑：

- backend
- sandbox
- MySQL
- Redis
- RabbitMQ
- 可能还有 Elasticsearch
- Docker daemon 本身

所以不能把 4 核 4G 全算给判题。

我的估算方法是：

- CPU 维度：判题属于偏重 CPU 和进程调度的任务，4 核机器不适合把判题并发直接开到 4
- 内存维度：虽然容器里限制了 100MB，但 Java 编译、运行、JVM、自身进程开销、Docker 开销不能只按 100MB 乐观估
- 系统维度：还要给数据库、中间件和操作系统留余量

所以在这种单机全家桶环境下，我会先保守定成：

- MQ 消费并发 = 1
- 判题线程池 = 1
- sandbox 并发许可 = 1

如果压测发现还有明显余量，再逐步往上调到 2。  
也就是说我不是按理论峰值配，而是按“稳定运行”的资源预算配。

面试里一句话可以说：

并发值是容量规划问题，不是功能参数。我会按 CPU、内存和单任务资源占用做预算，再从保守值起步，结合压测逐步调优。

### 如果一瞬间来 1000 个提交，系统行为是什么？排队、降级、超时、丢弃还是扩容？


如果一瞬间来了 1000 个提交，系统的行为如下：

1. 消息入队与阻塞
   所有的请求会首先进入 RabbitMQ 队列。由于系统设置了强制限制，这些请求会被阻挡在队列中进行排队。

2. 消费者限制
   目前只有 2 个消费者线程，每个消费者一次只能拉取 5 条消息。
   (a) 单次处理上限：系统一次性最多只能发放 10 条消息。
   (b) 线程池配置：虽然初始只有 2 条线程，但最大可扩展至 4 条线程。

3. 并发控制逻辑
   当线程池中的 4 条线程全部被占用后，剩下的 6 条消息（基于单次拉取的 10 条）会进入阻塞状态。
   (a) 同一时间，系统只能处理 4 条并发任务。
   (b) 这种机制保证了系统不会因为瞬间的高并发而崩溃。

4. 系统影响
   在这一瞬间，由于消费能力远低于入队速度，必然会导致消息在 RabbitMQ 中大量积压。

如果确实频繁遇到这种极端的高并发情况，最根本的解决办法还是升级服务器配置。



## API 签名鉴权

### - 你为什么选 API 签名，不选 JWT / OAuth2 / 网关鉴权？

### - 你的签名串由哪些字段组成？为什么要包含 body hash？
签名串包含以下字段，目前是由公钥、时间戳、随机数以及请求体组成的。在生成签名时，会使用密钥进行 SHA-256 加密。

之所以要带上 Body Hash，主要原因如下：

1. 弥补 Header 校验的不足：
   之前的 Header 校验范围不够全面。如果请求体（Body）被篡改，签名也必须随之失效。

2. 扩大校验范围：
   Body Hash 相当于将整个请求体都纳入了校验范围。

3. 保证数据完整性：
   这能保证代码内容、输入用例等核心信息在被篡改时，服务端能够发现签名与之前不一致，从而拦截非法请求。

## Docker 沙箱

  - 你的沙箱是不是一次判题创建一个临时容器？

对于代码沙箱部分，这里确实是采用“一次创建一个临时容器”的方案。

因为用户的行为是不可预测的，一次创建一个运行完之后立即销毁，主要是为了防止用户的恶意代码：
1. 防止用户编写死循环或无限递归，导致内存占满。
2. 防止用户编写病毒等恶意脚本，导致服务器崩溃。

通过一次一创、执行完即销毁的机制，可以最大限度地保证安全性。当然，目前的做法确实比较耗费资源（频繁地创建、运行再删除）。

后续的优化点：
1. 架构改进：
   我计划将其改为使用 Docker 容器集群，通过一个 Docker 池（Pool）来统一管理。
2. 现有安全措施：
   其实在创建 Docker 容器时，我已经采取了多重限制：
   (a) 禁止联网。
   (b) 设置了最大内存限制。
   (c) 增加了运行时间的监听。

所以目前基本上不太可能出现上述安全问题。

### 第一部分：你的自适应学习计划是如何实现的？请总体描述一下


首先，整体计划分为四个阶段。核心思路是建立一套学习路径，并根据不同的阶段采取相应的策略为用户分配题目。

具体实现分为以下几个模块：

1. 学习路径与知识点构建
   基于图数据库建立一个“考点图谱”，将所有知识点组织成类似“树”的结构。
   (a) 提取路径节点：从学习路径中抽取知识点（节点），按照一定规则进行排列。
   (b) 关联资源：每个知识点下都关联了相应的题目和讲解视频。

2. 阶段化题目分配
   整个计划包含四个阶段：理论学习、题目模块、实战和冲刺。
   (a) 系统会根据用户所处的阶段，应用不同的规则和策略来分配题目。
   (b) 系统会预先给出用户一周的学习计划，明确每天需要掌握的内容。

3. 动态调整机制
   学习计划是动态变化的。如果用户某天学的比较多，或者当天没有学习，系统会根据用户的实时动作进行动态调整。

4. 评估机制与指标
   通过多个维度的指标对用户的学习进度进行判断：
   (a) 周目标：例如完成周内所有任务，或至少完成 80%。
   (b) 阶段任务：设定预测分达标要求。
   (c) 量化指标：包括总学习时长、做题量以及任务完成比例。
   (d) 进度状态：判断计划是“崩溃”、“提前”还是达到了“最小要求”。

我主要负责的部分包括：考点路径的计算、阶段目标的计算，以及学习进度评估中的状态计算。



其中，考点路径的计算主要是基于我们之前的考点图谱。我们利用图数据库形成了一个类似于树形的考点图谱，将所有的知识点都包含在内，构建出一个层级结构。

考点路径的具体形成过程如下：

1. 获取根节点：
   从根节点开始向下递归，获取所有的子节点。

2. 排序与价值计算：
   在递归过程中，需要对节点进行排序。排序是根据“考点价值”来衡量的。
   考点价值是根据产品的预设公式，综合考点的分数、难度以及考评情况计算出来的。

3. 资源关联过滤：
   为了保证路径的有效性，如果某个节点没有关联任何学习资源，系统就不会将其记录到考点链中，而是直接将其剔除。

4. 链表构建：
   通过上述步骤，从底层向上层节点逐级连接，最终构建出一个完整的链表结构。

5. 用户偏好过滤：
   在链表构建完成后，还需要根据用户的偏好进行过滤。
   (a) 用户偏好（如希望先学什么、不想学什么）以数据表或数字图链的形式存储在数据库中。
   (b) 系统读取这些偏好数据，从已有的考点链中过滤掉不符合要求的内容。

最后，系统保留用户需要的考点路径并进行返回。这就是考点路径计算的核心逻辑。


### 学习计划的评估逻辑

关于学习计划的评估，其核心在于计算目标是否达成。目标主要分为总目标和阶段目标：

1. **目标达成标准**
   主要考察以下几个维度：
   (a) 是否达到预测分的标准
   (b) 学习时长是否足够
   (c) 完成的题目数量是否达标

   总目标和各个阶段目标都有各自预设的目标量。

2. **状态评估逻辑**
   评估是分阶段进行的，主要分为“周评估”和“阶段评估”，系统会根据计算结果给出相应的状态：

   * **周评估（已完成/进行中/无法完成）：**
     (a) **已完成：** 如果今天在周内且所有任务已完成，或者已经过了本周截止日且所有任务均已完成，状态为“已完成”。
     (b) **进行中：** 任务按计划推进，完全没有问题。
     (c) **无法完成：** 如果今天虽然在周内，但按照每周最大学习时长计算，已经无法完成剩余任务，则状态判定为“崩溃”（即无法完成）。

   * **阶段评估：**
     (a) 如果用户处在阶段中，但阶段考点路径里的所有考点都已学完，视为提前完成。
     (b) 如果在当前阶段内，模拟任务按照最大学习时长也无法完成，状态同样判定为“崩溃”。

3. **数据计算与技术实现**
   这里涉及两种计算法（周计算和阶段计算），采用的是从底层向上汇总数据的思路：

   * **数据维度：** 按照“天 → 周 → 阶段 → 整体”的维度层层递进。系统会从每天的节点中，将学习时长等属性累加起来，再按照预设规则进行判断。
   * **事件机制：** 采用基于事件的机制。当用户进入系统时，首先进行周判断。
   * **调用逻辑：** 周判断完成后，会同时进行周计算和阶段计算。系统会优先判断阶段状态，如果阶段已经处于“崩溃”状态，则直接调用相应逻辑；如果阶段没有崩溃，则继续正常的调用流程。



## 关于sub-agent

这里的 Memory tool 其实就是 Claude 官方指出的方向。他指出通过给 Claude 模型提供工具，让模型能够自主决定去调用这些工具。

具体实现上，你需要写好一个类似于文件系统的资源操作接口提供给它即可。我这部分主要做的是：

1. 使用阿里的对象存储 OSS
   (a) 构建了一套通过文件基本操作（以及修改文件）来实现的逻辑
   (b) 这包含了一套递进式的方案，以及一套通用的、在 OSS 中使用的模式



2. 学习计划评估逻辑与 Sub-Agent 内存工具

这个 Sub-Agent 的运作逻辑如下：

1. 主进程（Main Agent）职责：
   负责与用户进行交互，涵盖学习计划的相关咨询，包括计划调整、进度跟踪（如学习到哪一阶段了）以及提供相应的反馈等。

2. 子 Agent（Sub-Agent）职责：
   (a) 接入了专门的学科答疑模型，专门负责为用户提供学科内容的解答。
   (b) 该学科答疑模型被封装成了一个工具。

3. 调用流程：
   (a) 主进程负责判断用户的需求，如果识别到是学科答疑方面的问题，则会通过工具调用（Tool Calling）来启动子 Agent。
   (b) 调用完成后，系统将结果返回给主进程，由主进程统一向用户进行回答。



同时，系统还会触发学习状态的变更。例如，当学习状态重新启动或更新时，会向用户发送一个卡片，用户可以通过该卡片对之前的自适应学习计划进行调整。

这也是通过工具调用（Tool Calling）实现的，具体逻辑如下：

1. 处理用户个性化要求：
   当用户提出“不想学习当前内容”或“希望提前学习某项内容”时，系统会调用对应的修改工具。

2. 执行修改动作：
   (a) 修改考点路径。
   (b) 修改今日的学习内容。
   (c) 调用重新生成技术，更新学习计划。

## 关于 评测

这部分，主要是当时产品要求我们去测试另一个团队的“预测分身”模型是否可用。

为了测试这个结果的返回值是否符合预期，我们按照不同的场景进行了测试。

测试主要涵盖了单轮次和多轮次场景下，用户答题正确率起伏对“预测分”变化的影响。

以数学计算评测为例，测试流程如下：
1. 构造参数并请求接口：
   我们先去构造对应的参数并请求接口。
2. 汇总数据：
   请求接口后，将返回的 JSON 数据进行汇总。
3. 填充表格：
   由于测试用例（Case）非常多，最终我们会将汇总后的结果直接填入 Excel 表格中。

在具体的实现层面：
1. 自动化规划：
   考虑到测试场景的多样性，我直接调用了 AI 来做一个自动化的规划。
2. 函数调用与参数解析：
   通过编写一个内部函数，解析其中的不同参数。这些参数包括：
   (a) 题目信息：具体的题目编号。
   (b) 科目信息：该题目所属的科目。
   (c) 难度等级：题目的难易程度。
   (d) 答题状态：用户回答正确或错误的情况。
3. 模式匹配：
   根据解析出的不同参数，程序会切换到不同的模式（如 Tool, Agent, OSS, Claude 等）来获取预测结果，并最终将其填入 Excel。
